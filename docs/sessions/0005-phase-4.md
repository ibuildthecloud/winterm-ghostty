# Session 0005 — Phase 4: the WT seam (IControlCore)

Date: 2026-08-02 → 2026-08-03. Fork base: `microsoft/terminal` @ `ca7996296` (Phase 0 pin).
Branch: `windows` in `terminal/`.

## 1. Outcome

**Windows Terminal now runs on an interface rather than a concrete engine.** Everything the
shell consumes — ~90 members, 27 events — moved off `ControlCore` onto a new `IControlCore`
WinRT interface; `ControlCore` is a marker class implementing it, and `TermControl` holds
the interface. Six of the seven `get_self<ControlCore>` escapes are gone, replaced by IDL
members. The fork builds, launches, and passes the pre-fork test suites unchanged.

The per-profile `"engine"` setting is wired end to end, with `"cascadia"` the only valid
value and the only default, so the second engine can be added in Phase 5 without touching
the shell again.

## 4. Deviations

1. **`ControlInteractivity` still holds the concrete `ControlCore`.** ADR 0001 says both it
   and `TermControl` hold the interface. See §5 — this is the one open decision.
2. **`"engine"` is deliberately more permissive than every sibling enum setting.** See §5.
3. **The settings-editor UI was not touched.** `engine` is JSON-only this phase; it does not
   appear in the Settings UI and has no `EnumMappings` entry. Outside the exit criteria.
4. **Commits were split after the fact.** The first commit accidentally contained both
   workstreams under a seam-only message; it was reset and re-split into
   `8c23c1d6a` (seam) and `7dd1437bf` (engine setting) so the message matches the content.

## 5. Decisions needed

### 5.1 `ControlInteractivity` and the rest of the interface

ADR 0001 states the only invasive change is "mechanical MIDL promotion plus six call-site
fixes". That is true for `TermControl`. It is **not** true for `ControlInteractivity`, which
makes 58 calls across 34 distinct core methods, most of which are not part of the projected
contract at all:

> `AttachUiaEngine`, `DetachUiaEngine`, `SendMouseEvent`, `LeftClickOnTerminal`,
> `SetSelectionAnchor`, `SetEndSelectionPoint`, `GetRenderData`, `GetFont`, `GetHyperlink`,
> `CopySelectionToClipboard`, `CopyOnSelect`, `IsVtMouseModeEnabled`,
> `ShouldSendAlternateScroll`, `UserScrollViewport`, `AnchorContextMenu`,
> `AttachToNewControl`, `Detach`, `Close`, `GotFocus`, `LostFocus`, `UpdateSelectionMarkers`

Interface-typing it means promoting roughly twenty more members — the whole mouse, selection
and UIA surface. Phase 4's exit criteria do not require it, so it was left alone rather than
half-done.

**Recommendation:** treat this as an explicit Phase 5 prerequisite and amend ADR 0001's
"only invasive change" claim, which is now known to understate the work. A second engine
cannot function until `ControlInteractivity` is interface-typed, because it is the object
that actually drives input.

### 5.2 `"engine"` is uniquely permissive

Every other enum setting in WT hard-fails on an unrecognised value: `EnumMapper::FromJson`
throws `DeserializationError` and `SettingsLoader` rethrows it, producing an error dialog
with *none* of the user's settings applied. **This was verified by mutation, not assumed** —
reverting the tolerant trait reproduces exactly that, `* Line 16, Column 35 (engine)`.

The exit criterion asks for warn-and-fall-back, and that is right for this setting
specifically: `"ghostty"` is the value users will try first and stays unrecognised until
that engine ships, so a typo-grade mistake would break their whole settings file. But it
does make `engine` inconsistent with its siblings, and that inconsistency would likely be
argued in an upstream PR.

**Recommendation:** keep it. Revisit if the promotion is upstreamed, where the reviewer may
prefer consistency over friendliness.

## 6. Learnings for the plan

- **`Invoke-OpenConsoleTests` with no `-Test` hangs**, partway through the conhost
  `ScreenBufferTests`, taking the whole run with it. Always pass `-Test` and a timeout.
  Recorded in PLAN.md.
- **`nuget restore` needs `-SolutionDirectory`** unless invoked from the repo root; the
  wrapper does not pass it, so a stray `Set-Location` breaks restore with a misleading
  "Cannot determine the packages folder".
- **`-CleanCodegen` was missing `TerminalSettingsAppAdapterLib`.** That project keeps its own
  cppwinrt projection of `Microsoft.Terminal.Control` and consumes `ControlProperties.h`, so
  an IDL change that adds a type fails *there* first with a wall of "is not a member of
  `winrt::Microsoft::Terminal::Control`" — pointing at the consumer, never at the stale
  projection. Fixed in `scripts/build-terminal.ps1`.
- **Never run two WT builds concurrently.** They fight over the merged winmd
  (`MSB3027: file is locked by MSBuild.exe`) and the resulting errors look *identical* to the
  stale-codegen failure above, which cost real time to untangle. MSBuild also leaves node
  processes alive afterwards; kill them before rebuilding.
- **ADR 0001's escape count was six; the reality is seven.** The seventh is TSF. The ADR now
  carries the enumerated table.

## 7. Next-phase readiness gaps

Phase 5 is "Ghostty pane MVP inside Windows Terminal". From here:

- **§5.1 is a hard prerequisite**, not a nicety. Sequence it first.
- The `IControlCore` surface a second engine must satisfy is now concrete and readable in
  one file, `IControlCore.idl` — that is the actual obligation list, and it should be diffed
  against DESIGN.md's `GhosttyControlCore` obligation map before Phase 5 starts, since that
  map was written from an estimate.
- `IsBufferRowInViewport` and `SearchResultRows` are the two members whose shape was chosen
  for cascadia's implementation. Both look engine-neutral, but they are the ones most likely
  to need revisiting once a second engine implements them.
- Phase 5 will need the settings-editor UI work deferred in §4.3 if `engine` is to be
  selectable without hand-editing JSON.
