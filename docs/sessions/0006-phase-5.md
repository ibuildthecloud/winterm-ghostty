# Session 0006 — Phase 5 (Ghostty pane MVP inside Windows Terminal)

Date: 2026-08-04. Repos: `terminal/` @ `d3d0b6a27`, `ghostty/` @ `1fe550675` (patch 24).

## 1. Outcome

`"engine": "ghostty"` now builds a real second engine and Windows Terminal launches on
it: a ghostty profile opens, the window stays up, and beneath it sit
`OpenConsole.exe --headless --width 56 --height 18` and a live `cmd.exe`. All three of the
phase's work items exist — the `ControlInteractivity` promotion, `termio-external`, and
`GhosttyControlCore` — and the riskiest one was proven end to end in the harness before
any WinRT code was written. Separately, a user-reported crash turned out to be a
fork-wide defect that made **every non-ASCII byte** fatal; that is fixed.

**What is not established: that a ghostty pane renders pixels, or that typing reaches the
shell.** See §2 and §3.

## 2. Exit criteria

- [x] **A profile with `"engine": "ghostty"` opens a fully interactive shell in a WT tab.**
      Met, confirmed by the human at the machine: correct rendering, correct glyph size,
      the profile's Cascadia Mono and Campbell colours, and typing reaches the shell (a
      `dir` listing run by hand, its output parsed and drawn).

      Reaching it took four fixes past "it compiles", none of which the code review would
      have found — §4.6 through §4.9. Two are worth remembering because the pane looked
      *plausible* while broken: it came up blank because nothing was ever bound to the
      panel, and then came up magnified because XAML transforms what is bound.

      Side-by-side with a cascadia pane: **structurally confirmed** — one window, two
      ConPTYs, two shells, no crash. The visual was not captured (WGC intermittently
      returns no frame on this session), so "they both look right" is unconfirmed.
- [ ] **Tab title, resize, scrollback via scrollbar, close-confirmation all work.**
      Three of four met; the scrollbar drag still needs a hand on a mouse.

      - **Tab title — met.** `cmd /k title GHOSTTY_TITLE_PROBE` came out as WT's window
        title, which exercises the whole chain: child OSC → `write_pty_output` → ghostty's
        parser → `SET_TITLE` → marshalled `TitleChanged` → WT.
      - **Resize — met.** Growing the window moved the grid from `53x29` to `53x34` cells
        and pushed it through to the ConPTY. (Those traces also read `scale=2.000`: the
        window opened on a 200% monitor, so the DIP→pixel conversion is not tuned to one
        scale.)
      - **Scrollback via scrollbar — implemented, drag unverified.** `UserScrollViewport`
        was a **stub**, so this criterion was silently unmet until now; the scrollbar
        would have moved and the pane would not. It now uses `scroll_to_row`, whose
        absolute-row argument lines up with WT's `viewTop` directly. Confirming the drag
        needs a hand on a mouse.
      - **Close-confirmation — met by construction, and now understood.** It was
        recorded as untested because it was assumed to involve the core. It does not:
        `TerminalPage::_ShouldWarnOnClose` keys off the `confirmOnClose` setting plus
        the tab and pane counts, and never asks the core anything, so a ghostty pane
        cannot change the answer. The one engine-dependent part is the read-only close
        dialog, which reads `IControlCore::IsInReadOnlyMode` - implemented on
        `GhosttyControlCore`, and `SendInput` honours the flag. Both steps are on the
        manual checklist so the reasoning gets confirmed rather than trusted.
- [~] **Defterm handoff and an Azure-connection profile still work on both engines.**
      **Defterm: met on both engines** (see §10). **Azure: not testable here** - no Azure
      account with Cloud Shell is available on this machine, confirmed with the user. That
      half is not deferred, it is unmeetable as things stand, and should be picked up on a
      machine that has one rather than sitting on the ledger as if it were pending.

      The original text of this criterion follows, from when neither half had been tried.
      Not attempted, and **not attemptable unattended**: the Azure connection needs a real
      Azure account, and defterm handoff means changing the machine's default terminal,
      which is a system-wide setting on someone else's computer. Both need the human, and
      both should stay on the phase's ledger rather than being quietly dropped — this is
      the criterion that proves ADR 0006, so it matters more than its position here
      suggests.
- [x] **Screen-reader support on ghostty panes is out of scope** (stated in PLAN).
      Held: UIA stays cascadia-only, and TSF joined it — see §4.

## 4. Deviations

1. **`termio-external` blocks the producer but has no ring.** Decision A stands (the
   producer blocks); the parse happens on the caller's thread instead of behind a batch
   ring, because `ConptyConnection::_OutputThread` already overlaps a 128 KiB overlapped
   `ReadFile` with the previous `TerminalOutput.raise()`. A ring would duplicate that
   pipelining for a thread and a copy of every byte per surface. Recorded in
   `docs/phase-5-readiness.md` §Q2.
2. **The settings translator needed a new C API first, and got one.** `ghostty_config_t`
   had no setter entry point, so patch 25 added `ghostty_config_set(config, "key = value")` —
   one function that runs the entry through the config-file parser, rather than a setter
   per field, so every key and every value syntax works and future keys need no new API.
   All five PLAN fields are wired (font face/size, scrollback, scheme + 16 palette
   entries, padding). Padding is set to **zero** on purpose: WT already insets the panel by
   the profile's padding, and doubling it is what made the pane look bordered.
3. **Mouse input returns "not handled".** Keyboard, text and focus are wired; mouse,
   selection, search and marks return their empty answers. PLAN puts these in Phase 6, but
   it means the first ghostty pane is keyboard-only.
4. **TSF joined the accessibility deferral.** Phase 4 left `TsfDataProvider::_getCore` as
   the seventh `get_self` escape. It does not fail safe (§5), so `TermControl` now skips
   TSF registration entirely for engines that cannot back it.
5. **The engine bootstraps on its own 16 MB-reserve thread**, rather than raising
   `WindowsTerminal.exe`'s stack reserve.
6. **`SwapChainChanged` carries the handle in its args.** Raising it with null args - which
   reads as harmless - is what made the first pane blank.
   `TermControl::RenderEngineSwapChainChanged` unboxes a `uint64_t` from the args and never
   re-reads `SwapChainHandle()`, and it is the *only* place a normal startup binds the
   panel. So the wrong-looking-harmless call produced no binding at all rather than a late
   one. Fixed to box the handle the way `ControlCore` does.
7. **The surface is sized in physical pixels, not DIPs.** `TermControl` reports the panel in
   DIPs; `ghostty_surface_set_size` sizes a swap chain. Cascadia does the same multiply
   (`_panelWidth * _compositionScale`).
8. **XAML scales any swap chain bound to a `SwapChainPanel`** — patch 26. libghostty
   rendered 14px cells and 119 columns correctly and the compositor magnified it 1.5x and
   cropped to ~80 columns, which read as "the font is huge". The remedy is an inverse
   matrix via `IDXGISwapChain2::SetMatrixTransform`, which is what cascadia has always
   done. The binding for it was added in Phase 2, with a comment naming the slot, and never
   called. **This is a libghostty defect, not a WT one**, and it only appears in composition
   mode — which is why three phases of HWND harness work never saw it.
9. **Applying a config needs `ghostty_surface_update_config`.** A surface is born with the
   *app's* config; building one and translating into it is otherwise a silent no-op.

## 4a. FIXED: a ghostty pane stopped repainting on output

**Symptom.** Run `dir C:\Windows\System32` in a ghostty pane. The pane renders the first
~15% and then stops. The terminal is *not* stuck and no bytes are lost — scrolling reveals
the entire listing, correctly parsed and stored. Only the screen is stale.

**What does and does not force a repaint** (observed by the human at the machine):

| Action | Repaints? |
|---|---|
| New pty output | **no** |
| Resizing the window | **no** |
| Scrolling (wheel or scrollbar) | yes |

**Isolation.** Same libghostty build, same command, three configurations:

| Configuration | Result |
|---|---|
| `hwnd-host`: HWND + exec backend | completes the full listing |
| `hwnd-host`: HWND + **external** backend (`GHOSTTY_HARNESS_EXTERNAL=1`) | completes the full listing |
| WT pane: **composition** + external backend | freezes partway |

So `termio-external` is **not** implicated, and neither is the renderer generally. The
variable is **composition mode**, which is the one thing WT uses and neither harness run
does.

**Cause.** libghostty schedules repaints through its `wakeup` async, which **coalesces by
design** — the comment on the neighbouring `draw_now` says exactly that: *"This does not
coalesce like the wakeup does."* A notify arriving after the renderer has already sampled
the terminal state is folded into a wake that has finished its work, so the final batch
never reaches the screen.

Instrumented counters from one run settled it:

| Counter | Value |
|---|---|
| `queueRender` notifies | 80 |
| `processOutput` calls | 80 (58 KB parsed) |
| renderer thread wakes | < 20 |
| `drawFrame` invocations | stopped entirely |

Ruled out on the way, each with evidence rather than argument: lost bytes (the parser saw
everything); a skipped back-buffer copy (`present`'s size-mismatch branch never fired);
deadlock (every thread idle, both children at a `ReadConsoleW` prompt);
`must_draw_from_app_thread` (not declared for this apprt, so the renderer draws directly).

**Fix.** `GhosttyControlCore` calls `ghostty_surface_draw()` after handing each batch to the
engine. That is `drawFrame(sync = true)`, which skips the `needs_redraw` gate and is
documented as safe from another thread.

**Why three phases of harness work never caught it.** `hwnd-host` calls
`ghostty_surface_draw()` on every `WM_PAINT`. It has been force-drawing since Phase 1 and
masking this the whole time. A XAML pane has no paint pump, so it showed immediately.
**The composition-mode isolation in the table above was correlation, not cause** — recorded
as a fourth premature conclusion.

**Left open deliberately:** this is arguably compensating for an upstream shortcoming.
Output ought to drive its own repaint without the embedder forcing frames, and *any*
embedder not pumping paint messages would hit this. Worth raising upstream; the retro
should decide whether the fork carries a patch making the tail of the wakeup
non-coalescing instead of working around it here.

**Four wrong calls on the way here, recorded because the pattern matters more than any
one of them:**
1. "libghostty is slower in a Debug build." It was not slow, it was stale — two captures
   minutes apart were byte-identical.
2. "A resize forces the redraw." It does not; scrolling does. The recovery attributed to a
   resize was the human scrolling.
3. "`Detach()` revoked the connection handlers and we dropped the bytes." Impossible — a
   redraw revealed the content, so it had been parsed and stored all along.
4. "It is composition mode." Correlation. Composition is simply the configuration with no
   paint pump; the same defect was latent in the harness the whole time.

Each was offered before the evidence supported it, and in every case the human had
described the symptom accurately first. What finally worked was counters at four points in
the pipeline and reading the ratios.

## 4b. Open: performance

The pane felt laggy to the human evaluator. **Not investigated, and deliberately not
optimised against**, because the measurement would be worthless: libghostty is built
`-Doptimize=Debug` (Zig Debug leaves every safety check live in the VT parser and the
renderer) and Windows Terminal is a Debug build too. On top of that, until patch 26 the
compositor was rescaling every frame.

The honest next step is `.\scripts\build-ghostty.ps1 -Optimize ReleaseFast` with WT still
Debug, and only then a judgement. `scripts/bench-throughput.ps1` exists for the flood case
and has never been run against the WT path.

## 5. Decisions needed

None blocking. Two judgement calls worth ratifying at the retro:

- **`ghostty_config_set_*` is a new C API.** Deviation 2 cannot close without it. It is
  additive and upstreamable, and it is the natural next patch. Recommend doing it as
  patch 25 before any Phase 6 work, since every appearance setting depends on it.
- **libghostty's stack appetite is now a standing constraint.** Any future call into it
  from a WT-owned thread has to be checked. Recommend stating it in DESIGN.md rather than
  leaving it in a commit message.

## 6. Learnings for the plan

- **`get_self<T>` on a projected interface does not fail safe.** It yields a non-null
  garbage pointer, so `if (!p)` guards below such casts are decoration. Both surviving
  casts now QI for the `ControlCore` *class* interface first — testing for `IControlCore`
  would match every engine and be exactly as wrong. This deserves to be a rule in
  DESIGN.md, because it will recur for every remaining per-engine coupling.
- **An interface is not a seam until something else implements it.** Phase 4 promoted ~90
  members and declared the seam done; the first real second implementation found two ways
  through it in one afternoon (TSF's cast, and TSF's unchecked deref of what the provider
  returns). The lesson for Phase 6: expect the same from the couplings still marked
  "reimplement per engine".
- **ASCII-only smoke tests hid a total defect for two phases.** Every "it renders"
  criterion from here should include a non-ASCII line.
- **An event whose args carry a payload cannot be raised with null.** Three of this
  session's bugs share a shape: a call that looks inert but is load-bearing
  (`SwapChainChanged(nullptr)`), a cast that looks safe but yields a non-null wrong pointer
  (`get_self`), and a warning that looks derived but was hardcoded (`!= "cascadia"`). Each
  passed review by reading. Each was found by running it.
- **The engine list must live in one place.** `"ghostty"` warned as unrecognised while
  working, because the parser and the warning kept separate lists. The test that should
  have caught it was using `"ghostty"` as its example of an unknown engine - a test can
  pin a limitation in place as easily as a behaviour.
- **A debugger is worth more than an afternoon of hypotheses.** `winget install
  Microsoft.WinDbg` ships `cdb.exe` and needs no admin. Two theories reasoned from source
  were wrong; `dps`, `x` and `kp` settled it in minutes. Both WT crashes in this session
  were then diagnosed first try.

## 8. The non-ASCII crash (out of phase, but it blocked everything)

A report that `wsl aptitude` crashed the harness turned out to be far broader: **any
non-ASCII byte of terminal output** faulted, reading `0x78` through a virtual dispatch in
simdutf — a vtable slot off a null vptr, because `libghostty.dll` never ran its C++ static
initializers. Zig's DLL entry point does not run the `.CRT$XI*`/`.CRT$XC*` tables, and
upstream's `DllMain` only brought up vcrt/acrt, which cannot reach tables that live in our
image. Fixed in patch 24 by following MSVC's own startup order using the static CRT's own
markers and helpers. The load-bearing step is `__scrt_dllmain_before_initialize_c`, which
initializes the module's onexit tables: the first C++ initializer (`initlocks`) calls
`atexit`, and without it the CRT reallocs a garbage pointer.

Full account, including the two wrong theories and the retraction, in
`docs/research/crt-static-init-windows.md`. That file also records an **unreconciled Phase
3 result**: its CJK fixture exercises the faulting path yet passed in August. Build mode is
the plausible explanation and is flagged as a hypothesis to test, not a conclusion.

## 9. Second sitting — regression cover, and a deliverable that was not there

Everything above was found by hand. This part is about making sure it stays found, and
about one Phase 5 item that the code claimed to have and did not.

### 9.1 The fallback did not exist

PLAN's Phase 5 work list includes "engine init failure → `RendererEnteredErrorState` +
cascadia fallback", and two comments in the fork said that is what happened. Reading the
path end to end: `GhosttyControlCore::Initialize` returning false raises the error state,
`TermControl::_InitializeTerminal` returns false, and the pane is left dead. Nothing
anywhere built a cascadia core. The user is told and then stuck.

The fallback cannot work from `Initialize` at all — by the time it can report anything,
`TermControl` has bound its events to the core it was handed, and there is nothing left to
swap. So it moved to the engine factory: `ControlInteractivity` asks
`GhosttyEngine::TryGet()` before committing, and builds a cascadia core when the engine is
not there. A *surface* that fails later still takes the error-state route, deliberately —
that failure is per-pane and the session may already have output in it.

`GhosttyEngine::_unavailableForTests` was added in the shape `ControlCore::_inUnitTests`
already uses. A machine where libghostty will not start is not a state a test can reach by
asking, and an untested fallback is one nobody has seen work.

### 9.2 What is now covered, and how it was checked

Every test below was mutation-verified: the behaviour was reverted, the test was confirmed
to fail, and the other tests were confirmed not to.

| Bug it came from | Test |
| --- | --- |
| Font family with a space silently truncated | `GhosttySettingsTests::FontFamilyIsQuoted` |
| WT's "infinite" scrollback forwarded as a negative limit | `InfiniteScrollbackIsNotForwarded` |
| Pane inset twice, which read as a border | `PaddingIsZeroBecauseWindowsTerminalAlreadyPads` |
| Colours not reaching the engine | `SchemeProducesForegroundBackgroundAndFullPalette` |
| The fallback above | `GhosttyEngineSelectionTests::GhosttyFallsBackToCascadiaWhenTheEngineIsUnavailable` |
| Non-ASCII output killing the process (patch 24) | `scripts\smoke-harness.ps1` check 1 |
| Output never reaching the screen | `scripts\smoke-harness.ps1` check 3 |

The settings translation moved into its own translation unit to be testable at all: it is
a pure function over `IControlSettings`, so it compiles into the test binary with no
engine, GPU or pty. The rest of `GhosttyControlCore` needs a live surface and stays out of
reach.

Check 1 was verified the honest way — the static-initializer bootstrap was removed from
`src/main_c.zig`, libghostty rebuilt, and the check failed with the original `0xC0000005`
and named its cause.

Counts: `unitControl` 32 → 42, `unitSettingsModel` 159/159, harness smoke 3/3.

### 9.3 What could not be tested, stated plainly

**The repaint freeze has no automated cover.** Check 3 captures the window, makes the
child print, and requires a large fraction of the pixels to change — but removing Windows
Terminal's post-write render call leaves it passing, because the harness's own wakeup path
repaints anyway. It guards the path being alive, not the coalescing bug. Item 1 of
`docs/manual-validation.md` still needs a human, an unfocused pane, and a hand kept off
the mouse.

The harness deliberately does *not* render after writing output, though WT's control does.
Keeping it on libghostty's own behaviour is what would let the two disagree visibly;
compensating there would hide the finding.

### 9.4 Two traps worth carrying forward

- **Redirecting the harness's stdout, or launching it with `-NoNewWindow`, breaks the
  ConPTY child's console attach.** cmd.exe reads EOF and exits 0 while conhost keeps
  rendering an empty screen — which looks *exactly* like a renderer that stopped painting.
  An hour went into that diagnosis, including a wrong conclusion stated out loud that the
  harness had reproduced the repaint bug. It had not; the launcher was broken. `cdb`'s
  thread stacks and a byte-level trace of the pty settled it: the reader was idle in
  `ReadFile`, and the child had already exited.
- **`nuget restore` in `build-terminal.ps1`** derived its packages folder from the current
  directory, so it only worked when run from inside `terminal/`. Now passes
  `-PackagesDirectory` explicitly.

## 10. Defterm handoff — met, and the input bug it exposed

Done at the machine with the user, who changed the default terminal application to the
dev build for the duration and changed it back afterwards. The prior values were recorded
first (`DelegationConsole {2EACA947-…}` / `DelegationTerminal {E12CFF52-…}`, the released
Windows Terminal) so the restore was exact. The dev package registers *different* CLSIDs
(`{1F9F2BF5-…}` / `{051F34EE-…}`), which is why the setting had to change at all.

Both engines pass. A `cmd.exe` launched outside any terminal is handed off to the fork,
and with the ghostty engine on the profile the handoff resolves to, the pane renders the
child and takes input: a full `dir` typed by hand, rendered and scrolled correctly.

Verified by thread dump rather than by looking at the window, which matters — see §10.2.
The passing configuration shows, in one process: one `ConptyConnection Output Thread`
(Windows Terminal owns the pty), one libghostty `renderer`/`io` pair (ghostty owns the
rendering), and `GhosttyEngine::_tickLoop`. That is ADR 0006 stated as a fact about a
running process.

### 10.1 `defaultProfile` is the wrong lever

A defterm handoff does **not** open the default profile. `CreateTabFromConnection` copies
the handed-off process's commandline into the args, and `GetProfileForArgs` matches it
against the profile list via `_getProfileForCommandLine`. So a handed-off `cmd.exe`
resolves to the **Command Prompt** profile, and `defaultProfile` is never consulted; had
nothing matched, the fallback is the *defaults* block, still not `defaultProfile`.

This is stock Windows Terminal behaviour, not something the fork introduced. To exercise
an engine through defterm, put `"engine"` on the profile whose commandline the handoff
matches.

### 10.2 A claim made too early, and retracted

Criterion 3 was reported here as "met on both engines" **before** it had been established
which engine the pane was actually on. The evidence used was a tab titled `ghostty test`
and the presence of libghostty threads in the process — but the window had other tabs, and
the threads belonged to one of those. A clean single-tab run showed **zero** libghostty
surfaces: the handoff was on cascadia the whole time.

The user's `Ctrl+Shift+T` was what separated the possibilities: it opened a working ghostty
tab in the same process, proving the engine was healthy and the problem was profile
resolution, not the engine. Two candidate explanations had been on the table — the handoff
not carrying the engine, versus the new cascadia fallback firing silently — and they are
very different bugs. A three-frame thread dump would have settled it at the start; a tab
title never could.

### 10.3 Keyboard input in a ghostty pane was sending the wrong keys

Found because typing `cd` in the handed-off pane opened cmd's F9 prompt.

`TrySendKeyEvent` assigned the Win32 **virtual key** to `ghostty_input_key_s::keycode`.
That field is the *native* platform keycode — on Windows the **scan code**, `0xE000`-
prefixed for extended keys, resolved against ghostty's `src/input/keycodes.zig`. A virtual
key there lands on whatever unrelated key shares the number, so `d` arrived as a different
key and ate a character. The correct value was already a parameter, discarded one line
below by `UNREFERENCED_PARAMETER(scanCode)`.

**Why it survived earlier testing.** Printable characters arrive separately through
`SendCharEvent` → `ghostty_surface_text`, which was always correct. So typing looked like
it worked; every keypress was *also* firing a bogus second key, and only some of those do
anything visible. The Phase 5 sign-off "typing reaches the shell (a `dir` run by hand)"
was true and still concealed this.

The fix also sends the key's text and unshifted codepoint, ported from the harness's
`winkeys.c` — which had this right from Phase 3 and carried the reasoning next to it:
control characters must **not** be forwarded as text, because ghostty's `key_encode` short
circuits on a non-empty `utf8` field and they would replace its own encoding of the key.
The text must be present, because `TermControl` treats a handled key as translated and
suppresses the `CharacterReceived` event that would otherwise carry the character.

Two harnesses solving the same problem, one of them correctly, and the correct one was not
consulted when the second was written. Worth remembering when Phase 6 wires mouse input:
`winkeys.c` is the reference.
