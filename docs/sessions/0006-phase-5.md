# Session 0006 — Phase 5 (Ghostty pane MVP inside Windows Terminal)

Date: 2026-08-04. Repos: `terminal/` @ `d3d0b6a27`, `ghostty/` @ `1fe550675` (patch 24).

## 1. Outcome

`"engine": "ghostty"` now builds a real second engine and Windows Terminal launches on
it: a ghostty profile opens, the window stays up, and beneath it sit
`OpenConsole.exe --headless --width 56 --height 18` and a live `cmd.exe`. All three of the
phase's work items exist — the `ControlInteractivity` promotion, `termio-external`, and
`GhosttyControlCore` — and the riskiest one was proven end to end in the harness before
any WinRT code was written. Separately, a user-reported crash turned out to be a
fork-wide defect that made **every non-ASCII byte** fatal; that is fixed.

**What is not established: that a ghostty pane renders pixels, or that typing reaches the
shell.** See §2 and §3.

## 2. Exit criteria

- [x] **A profile with `"engine": "ghostty"` opens a fully interactive shell in a WT tab.**
      Met, confirmed by the human at the machine: correct rendering, correct glyph size,
      the profile's Cascadia Mono and Campbell colours, and typing reaches the shell (a
      `dir` listing run by hand, its output parsed and drawn).

      Reaching it took four fixes past "it compiles", none of which the code review would
      have found — §4.6 through §4.9. Two are worth remembering because the pane looked
      *plausible* while broken: it came up blank because nothing was ever bound to the
      panel, and then came up magnified because XAML transforms what is bound.

      Side-by-side with a cascadia pane: **structurally confirmed** — one window, two
      ConPTYs, two shells, no crash. The visual was not captured (WGC intermittently
      returns no frame on this session), so "they both look right" is unconfirmed.
- [ ] **Tab title, resize, scrollback via scrollbar, close-confirmation all work.**
      Three of four; one untested.

      - **Tab title — met.** `cmd /k title GHOSTTY_TITLE_PROBE` came out as WT's window
        title, which exercises the whole chain: child OSC → `write_pty_output` → ghostty's
        parser → `SET_TITLE` → marshalled `TitleChanged` → WT.
      - **Resize — met.** Growing the window moved the grid from `53x29` to `53x34` cells
        and pushed it through to the ConPTY. (Those traces also read `scale=2.000`: the
        window opened on a 200% monitor, so the DIP→pixel conversion is not tuned to one
        scale.)
      - **Scrollback via scrollbar — implemented, drag unverified.** `UserScrollViewport`
        was a **stub**, so this criterion was silently unmet until now; the scrollbar
        would have moved and the pane would not. It now uses `scroll_to_row`, whose
        absolute-row argument lines up with WT's `viewTop` directly. Confirming the drag
        needs a hand on a mouse.
      - **Close-confirmation — not tested.**
- [ ] **Defterm handoff and an Azure-connection profile still work on both engines.**
      Not attempted, and **not attemptable unattended**: the Azure connection needs a real
      Azure account, and defterm handoff means changing the machine's default terminal,
      which is a system-wide setting on someone else's computer. Both need the human, and
      both should stay on the phase's ledger rather than being quietly dropped — this is
      the criterion that proves ADR 0006, so it matters more than its position here
      suggests.
- [x] **Screen-reader support on ghostty panes is out of scope** (stated in PLAN).
      Held: UIA stays cascadia-only, and TSF joined it — see §4.

## 4. Deviations

1. **`termio-external` blocks the producer but has no ring.** Decision A stands (the
   producer blocks); the parse happens on the caller's thread instead of behind a batch
   ring, because `ConptyConnection::_OutputThread` already overlaps a 128 KiB overlapped
   `ReadFile` with the previous `TerminalOutput.raise()`. A ring would duplicate that
   pipelining for a thread and a copy of every byte per surface. Recorded in
   `docs/phase-5-readiness.md` §Q2.
2. **The settings translator needed a new C API first, and got one.** `ghostty_config_t`
   had no setter entry point, so patch 25 added `ghostty_config_set(config, "key = value")` —
   one function that runs the entry through the config-file parser, rather than a setter
   per field, so every key and every value syntax works and future keys need no new API.
   All five PLAN fields are wired (font face/size, scrollback, scheme + 16 palette
   entries, padding). Padding is set to **zero** on purpose: WT already insets the panel by
   the profile's padding, and doubling it is what made the pane look bordered.
3. **Mouse input returns "not handled".** Keyboard, text and focus are wired; mouse,
   selection, search and marks return their empty answers. PLAN puts these in Phase 6, but
   it means the first ghostty pane is keyboard-only.
4. **TSF joined the accessibility deferral.** Phase 4 left `TsfDataProvider::_getCore` as
   the seventh `get_self` escape. It does not fail safe (§5), so `TermControl` now skips
   TSF registration entirely for engines that cannot back it.
5. **The engine bootstraps on its own 16 MB-reserve thread**, rather than raising
   `WindowsTerminal.exe`'s stack reserve.
6. **`SwapChainChanged` carries the handle in its args.** Raising it with null args - which
   reads as harmless - is what made the first pane blank.
   `TermControl::RenderEngineSwapChainChanged` unboxes a `uint64_t` from the args and never
   re-reads `SwapChainHandle()`, and it is the *only* place a normal startup binds the
   panel. So the wrong-looking-harmless call produced no binding at all rather than a late
   one. Fixed to box the handle the way `ControlCore` does.
7. **The surface is sized in physical pixels, not DIPs.** `TermControl` reports the panel in
   DIPs; `ghostty_surface_set_size` sizes a swap chain. Cascadia does the same multiply
   (`_panelWidth * _compositionScale`).
8. **XAML scales any swap chain bound to a `SwapChainPanel`** — patch 26. libghostty
   rendered 14px cells and 119 columns correctly and the compositor magnified it 1.5x and
   cropped to ~80 columns, which read as "the font is huge". The remedy is an inverse
   matrix via `IDXGISwapChain2::SetMatrixTransform`, which is what cascadia has always
   done. The binding for it was added in Phase 2, with a comment naming the slot, and never
   called. **This is a libghostty defect, not a WT one**, and it only appears in composition
   mode — which is why three phases of HWND harness work never saw it.
9. **Applying a config needs `ghostty_surface_update_config`.** A surface is born with the
   *app's* config; building one and translating into it is otherwise a silent no-op.

## 4a. OPEN DEFECT: a ghostty pane stops repainting on output (composition mode)

**Symptom.** Run `dir C:\Windows\System32` in a ghostty pane. The pane renders the first
~15% and then stops. The terminal is *not* stuck and no bytes are lost — scrolling reveals
the entire listing, correctly parsed and stored. Only the screen is stale.

**What does and does not force a repaint** (observed by the human at the machine):

| Action | Repaints? |
|---|---|
| New pty output | **no** |
| Resizing the window | **no** |
| Scrolling (wheel or scrollbar) | yes |

**Isolation.** Same libghostty build, same command, three configurations:

| Configuration | Result |
|---|---|
| `hwnd-host`: HWND + exec backend | completes the full listing |
| `hwnd-host`: HWND + **external** backend (`GHOSTTY_HARNESS_EXTERNAL=1`) | completes the full listing |
| WT pane: **composition** + external backend | freezes partway |

So `termio-external` is **not** implicated, and neither is the renderer generally. The
variable is **composition mode**, which is the one thing WT uses and neither harness run
does.

**Not yet explained.** Ruled out along the way: `must_draw_from_app_thread` (not declared
for the embedded apprt, so the renderer draws directly rather than asking the embedder);
threads deadlocking (at the freeze, both libghostty threads are idle in
`GetQueuedCompletionStatusEx`, both `ConptyConnection::_OutputThread`s are idle in
`GetOverlappedResultSameThread`, and both `cmd.exe` children sit in `ReadConsoleW` at a
prompt — nothing is blocked and the child finished writing).

The remaining suspects are all inside `drawFrame`'s redraw gate
(`size_changed or cells_rebuilt or hasAnimations or sync`, else `presentLastTarget()`) and
the composition presentation path. **`harness/xaml-host` already binds a SwapChainPanel and
is the right place to reproduce this away from WT**, which is where the next session should
start rather than instrumenting inside Windows Terminal.

**Two wrong calls on the way here, recorded because both were premature:**
1. First read as "libghostty is slower in a Debug build". It is not slow, it is stale — two
   captures minutes apart were byte-identical.
2. Then read as "a resize forces the redraw". It does not; scrolling does. The recovery
   attributed to a resize was actually the human scrolling.

Both were explanations offered before the evidence supported them, on a symptom the human
had already described accurately.

## 4b. Open: performance

The pane felt laggy to the human evaluator. **Not investigated, and deliberately not
optimised against**, because the measurement would be worthless: libghostty is built
`-Doptimize=Debug` (Zig Debug leaves every safety check live in the VT parser and the
renderer) and Windows Terminal is a Debug build too. On top of that, until patch 26 the
compositor was rescaling every frame.

The honest next step is `.\scripts\build-ghostty.ps1 -Optimize ReleaseFast` with WT still
Debug, and only then a judgement. `scripts/bench-throughput.ps1` exists for the flood case
and has never been run against the WT path.

## 5. Decisions needed

None blocking. Two judgement calls worth ratifying at the retro:

- **`ghostty_config_set_*` is a new C API.** Deviation 2 cannot close without it. It is
  additive and upstreamable, and it is the natural next patch. Recommend doing it as
  patch 25 before any Phase 6 work, since every appearance setting depends on it.
- **libghostty's stack appetite is now a standing constraint.** Any future call into it
  from a WT-owned thread has to be checked. Recommend stating it in DESIGN.md rather than
  leaving it in a commit message.

## 6. Learnings for the plan

- **`get_self<T>` on a projected interface does not fail safe.** It yields a non-null
  garbage pointer, so `if (!p)` guards below such casts are decoration. Both surviving
  casts now QI for the `ControlCore` *class* interface first — testing for `IControlCore`
  would match every engine and be exactly as wrong. This deserves to be a rule in
  DESIGN.md, because it will recur for every remaining per-engine coupling.
- **An interface is not a seam until something else implements it.** Phase 4 promoted ~90
  members and declared the seam done; the first real second implementation found two ways
  through it in one afternoon (TSF's cast, and TSF's unchecked deref of what the provider
  returns). The lesson for Phase 6: expect the same from the couplings still marked
  "reimplement per engine".
- **ASCII-only smoke tests hid a total defect for two phases.** Every "it renders"
  criterion from here should include a non-ASCII line.
- **An event whose args carry a payload cannot be raised with null.** Three of this
  session's bugs share a shape: a call that looks inert but is load-bearing
  (`SwapChainChanged(nullptr)`), a cast that looks safe but yields a non-null wrong pointer
  (`get_self`), and a warning that looks derived but was hardcoded (`!= "cascadia"`). Each
  passed review by reading. Each was found by running it.
- **The engine list must live in one place.** `"ghostty"` warned as unrecognised while
  working, because the parser and the warning kept separate lists. The test that should
  have caught it was using `"ghostty"` as its example of an unknown engine - a test can
  pin a limitation in place as easily as a behaviour.
- **A debugger is worth more than an afternoon of hypotheses.** `winget install
  Microsoft.WinDbg` ships `cdb.exe` and needs no admin. Two theories reasoned from source
  were wrong; `dps`, `x` and `kp` settled it in minutes. Both WT crashes in this session
  were then diagnosed first try.

## 8. The non-ASCII crash (out of phase, but it blocked everything)

A report that `wsl aptitude` crashed the harness turned out to be far broader: **any
non-ASCII byte of terminal output** faulted, reading `0x78` through a virtual dispatch in
simdutf — a vtable slot off a null vptr, because `libghostty.dll` never ran its C++ static
initializers. Zig's DLL entry point does not run the `.CRT$XI*`/`.CRT$XC*` tables, and
upstream's `DllMain` only brought up vcrt/acrt, which cannot reach tables that live in our
image. Fixed in patch 24 by following MSVC's own startup order using the static CRT's own
markers and helpers. The load-bearing step is `__scrt_dllmain_before_initialize_c`, which
initializes the module's onexit tables: the first C++ initializer (`initlocks`) calls
`atexit`, and without it the CRT reallocs a garbage pointer.

Full account, including the two wrong theories and the retraction, in
`docs/research/crt-static-init-windows.md`. That file also records an **unreconciled Phase
3 result**: its CJK fixture exercises the faulting path yet passed in August. Build mode is
the plausible explanation and is flagged as a hypothesis to test, not a conclusion.
