# Session 0006 — Phase 5 (Ghostty pane MVP inside Windows Terminal)

Date: 2026-08-04. Repos: `terminal/` @ `d3d0b6a27`, `ghostty/` @ `1fe550675` (patch 24).

## 1. Outcome

`"engine": "ghostty"` now builds a real second engine and Windows Terminal launches on
it: a ghostty profile opens, the window stays up, and beneath it sit
`OpenConsole.exe --headless --width 56 --height 18` and a live `cmd.exe`. All three of the
phase's work items exist — the `ControlInteractivity` promotion, `termio-external`, and
`GhosttyControlCore` — and the riskiest one was proven end to end in the harness before
any WinRT code was written. Separately, a user-reported crash turned out to be a
fork-wide defect that made **every non-ASCII byte** fatal; that is fixed.

**What is not established: that a ghostty pane renders pixels, or that typing reaches the
shell.** See §2 and §3.

## 4. Deviations

1. **`termio-external` blocks the producer but has no ring.** Decision A stands (the
   producer blocks); the parse happens on the caller's thread instead of behind a batch
   ring, because `ConptyConnection::_OutputThread` already overlaps a 128 KiB overlapped
   `ReadFile` with the previous `TerminalOutput.raise()`. A ring would duplicate that
   pipelining for a thread and a copy of every byte per surface. Recorded in
   `docs/phase-5-readiness.md` §Q2.
2. **The settings translator is a no-op.** PLAN scopes it to five fields; `ghostty_config_t`
   has no C setter entry point, so there is nothing to translate *into* yet. Populating it
   through CLI-style strings would have been a fake. A ghostty pane renders with ghostty's
   defaults. **This is an unmet part of a phase item, not a finished one.**
3. **Mouse input returns "not handled".** Keyboard, text and focus are wired; mouse,
   selection, search and marks return their empty answers. PLAN puts these in Phase 6, but
   it means the first ghostty pane is keyboard-only.
4. **TSF joined the accessibility deferral.** Phase 4 left `TsfDataProvider::_getCore` as
   the seventh `get_self` escape. It does not fail safe (§5), so `TermControl` now skips
   TSF registration entirely for engines that cannot back it.
5. **The engine bootstraps on its own 16 MB-reserve thread**, rather than raising
   `WindowsTerminal.exe`'s stack reserve.
6. **`SwapChainChanged` carries the handle in its args.** Raising it with null args - which
   reads as harmless - is what made the first pane blank.
   `TermControl::RenderEngineSwapChainChanged` unboxes a `uint64_t` from the args and never
   re-reads `SwapChainHandle()`, and it is the *only* place a normal startup binds the
   panel. So the wrong-looking-harmless call produced no binding at all rather than a late
   one. Fixed to box the handle the way `ControlCore` does.

## 5. Decisions needed

None blocking. Two judgement calls worth ratifying at the retro:

- **`ghostty_config_set_*` is a new C API.** Deviation 2 cannot close without it. It is
  additive and upstreamable, and it is the natural next patch. Recommend doing it as
  patch 25 before any Phase 6 work, since every appearance setting depends on it.
- **libghostty's stack appetite is now a standing constraint.** Any future call into it
  from a WT-owned thread has to be checked. Recommend stating it in DESIGN.md rather than
  leaving it in a commit message.

## 6. Learnings for the plan

- **`get_self<T>` on a projected interface does not fail safe.** It yields a non-null
  garbage pointer, so `if (!p)` guards below such casts are decoration. Both surviving
  casts now QI for the `ControlCore` *class* interface first — testing for `IControlCore`
  would match every engine and be exactly as wrong. This deserves to be a rule in
  DESIGN.md, because it will recur for every remaining per-engine coupling.
- **An interface is not a seam until something else implements it.** Phase 4 promoted ~90
  members and declared the seam done; the first real second implementation found two ways
  through it in one afternoon (TSF's cast, and TSF's unchecked deref of what the provider
  returns). The lesson for Phase 6: expect the same from the couplings still marked
  "reimplement per engine".
- **ASCII-only smoke tests hid a total defect for two phases.** Every "it renders"
  criterion from here should include a non-ASCII line.
- **An event whose args carry a payload cannot be raised with null.** Three of this
  session's bugs share a shape: a call that looks inert but is load-bearing
  (`SwapChainChanged(nullptr)`), a cast that looks safe but yields a non-null wrong pointer
  (`get_self`), and a warning that looks derived but was hardcoded (`!= "cascadia"`). Each
  passed review by reading. Each was found by running it.
- **The engine list must live in one place.** `"ghostty"` warned as unrecognised while
  working, because the parser and the warning kept separate lists. The test that should
  have caught it was using `"ghostty"` as its example of an unknown engine - a test can
  pin a limitation in place as easily as a behaviour.
- **A debugger is worth more than an afternoon of hypotheses.** `winget install
  Microsoft.WinDbg` ships `cdb.exe` and needs no admin. Two theories reasoned from source
  were wrong; `dps`, `x` and `kp` settled it in minutes. Both WT crashes in this session
  were then diagnosed first try.

## 8. The non-ASCII crash (out of phase, but it blocked everything)

A report that `wsl aptitude` crashed the harness turned out to be far broader: **any
non-ASCII byte of terminal output** faulted, reading `0x78` through a virtual dispatch in
simdutf — a vtable slot off a null vptr, because `libghostty.dll` never ran its C++ static
initializers. Zig's DLL entry point does not run the `.CRT$XI*`/`.CRT$XC*` tables, and
upstream's `DllMain` only brought up vcrt/acrt, which cannot reach tables that live in our
image. Fixed in patch 24 by following MSVC's own startup order using the static CRT's own
markers and helpers. The load-bearing step is `__scrt_dllmain_before_initialize_c`, which
initializes the module's onexit tables: the first C++ initializer (`initlocks`) calls
`atexit`, and without it the CRT reallocs a garbage pointer.

Full account, including the two wrong theories and the retraction, in
`docs/research/crt-static-init-windows.md`. That file also records an **unreconciled Phase
3 result**: its CJK fixture exercises the faulting path yet passed in August. Build mode is
the plausible explanation and is flagged as a hypothesis to test, not a conclusion.
