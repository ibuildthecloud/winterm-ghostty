## KD-06 — a ligature's second half blinks with the cursor

Reported from use: type `--` at a prompt, move the cursor back onto the **first** dash,
and the **second** dash blinks in antiphase with the block cursor.

### What was measured

Frames of a live pane captured with `harness/wgc-shot`, diffed per pixel. Cells are
13 px wide, column 0 starts at x=18, so one cell is 338 px of 13x26.

| line | cursor parked on | pixels changing per blink |
|---|---|---|
| `--` | first dash | **365 px, x=[239..261] — two cells** |
| `--` | second dash | 331 px — one cell |
| `xy` | first letter | 338 px — one cell |

Only the first case leaks past the cursor's own cell, and only on the three pixel rows
carrying the dash's ink. A glyph disappearing, not a rectangle painting over one.

### Cause

ghostty breaks shaping runs at the cursor (`font/shaper/run.zig:178`) so a ligature under
the cursor is split into its components. That break is only applied when the row is
re-shaped, and `renderer/generic.zig:2408-2410` re-shapes a row only when it is dirty:

```zig
if (!rebuild) {
    if (!dirty.*) continue;
```

Moving the cursor changes no cell contents, so the row is never re-shaped. The `--` keeps
the ligature shaping it was given while the cursor was still to its right — one glyph,
owned by the first cell, spanning two — and drawing the cursor block over that cell takes
the ligature's right half with it.

### Confirmed, not merely argued

`FontShapingBreak.cursor` was temporarily defaulted to `false`, libghostty rebuilt and
deployed. That knob **disables** the break, so it predicts the symptom becomes universal
— including in the write-and-move-in-one-burst case that renders correctly today.
Predicting a change in a case that *works* is a sharper test than watching a symptom
vanish.

| case | break on | break off |
|---|---|---|
| `…q--`, cursor on first dash | 338 px — correct | **365 px, identical range to the bug** |
| `…qxy`, cursor on the `x` | 338 px | 338 px — unchanged |

Reverted afterwards and re-measured back to 338 px, which is what confirms the revert —
not a file hash, since the previously deployed DLL predated current HEAD anyway.

### Method note worth keeping

**Four printf-based repro attempts failed before the mechanism was clear**, and the
reason is general: writing the text and the cursor movement in one burst means the
renderer's *first* shaping of that row already has the cursor in place, so nothing is
stale. Inserting a pause reproduces it with no shell, no readline and no typing. Any
repro that emits content and cursor movement together will report this defect as absent.

Also cost real time: four capture runs went to the wrong profile. The default profile is
**"Ubuntu"** (`{51855cb2-…}`, `cursorShape: filledBox`); `Ubuntu-24.04` is a different,
hidden, auto-generated profile with no cursorShape, which is why every attempt showed a
bar cursor and no block to blink.

## Packaging

### The decision the plan flagged, resolved

Phase 8's open question — "signing/identity for the MSIX (test cert vs proper
identity)" — was put to the gate and answered: **self-signed certificate**, package
identity `WintermGhostty`, display name "Windows Terminal (ghostty)", publisher
`CN=Darren Shepherd`.

The identity change was not optional, for three independent reasons:

1. An MSIX signature is valid only when the certificate subject matches `Publisher`
   exactly. Upstream's `CN=Microsoft Corporation, …` is unsignable by anyone else.
2. It would ship an artifact identifying itself as Microsoft's.
3. `Name` forms the package family, so `WindowsTerminalDev` would have **replaced** a
   real Windows Terminal Dev install rather than sitting beside one.

The execution alias moved to `wtg.exe` for a related reason: an alias is machine-global,
and claiming `wtd.exe` would take it from a Dev install — precisely this audience. Zero
references to the alias existed in this repo, so the rename cost nothing here.

### What was built

- **terminal patch 45** — manifest identity, branding strings, alias; `WtExeUtils.h`
  follows both halves (`WtdExe` → `wtg.exe`, `IsDevBuild()` matches the new name), else
  the shell extension resolves a path that does not exist and "Open in Terminal" breaks
  silently.
- **`scripts/package.ps1`** — builds, signs and stages `dist/`: the `.msix`, the `.cer`,
  the `Microsoft.UI.Xaml.2.8` framework package, and `SHA256SUMS.txt`.
- **`docs/install.md`** — install, engine opt-in, and two things a download page usually
  skips: what trusting a self-signed certificate actually grants, and the CLSID conflict
  below.
- **[v0.1.0](https://github.com/ibuildthecloud/winterm-ghostty/releases/tag/v0.1.0)** —
  published, four assets, 38.5 MB package.

Two traps encoded in the script rather than in a comment somewhere:

- `signtool verify` reports an untrusted chain for a self-signed package. That is
  correct behaviour, so it is swallowed deliberately — left in `$LASTEXITCODE` it makes
  a good packaging run look failed.
- The WinUI framework package ships even though most machines have it, because when it
  is missing `Add-AppxPackage` fails with a bare `0x80073CF3` naming no dependency.

Also learned: `Executable` in the appExecutionAlias extension names a file **inside the
package**, and MakeAppx rejects one that is not there. Only `Alias` is the global name,
and the two need not match.

### Not verified

**Nobody has installed the artifact.** The session had no elevation, so importing the
certificate into `LocalMachine\TrustedPeople` and running `Add-AppxPackage` were never
executed. The package is signed, timestamped and structurally valid, and its identity was
read back out of the built `.msix` rather than assumed — but "it installs" is untested,
and the release is public. First thing to check next session, or by hand:

```powershell
# elevated
Import-Certificate -FilePath .\winterm-ghostty-0.1.0.0.cer -CertStoreLocation Cert:\LocalMachine\TrustedPeople
# not elevated
Add-AppxPackage -Path .\winterm-ghostty-0.1.0.0-x64.msix -DependencyPath .\Microsoft.UI.Xaml.2.8.appx
```

### Known limitation shipped knowingly

The COM class IDs for the shell extension, the "Open in Terminal" verb and
default-terminal handoff are inherited unchanged from upstream. A machine with Windows
Terminal **Dev** installed will have two packages registering the same CLSIDs, and the
last to register wins. Changing them means changing them in C++ too, so it was recorded
in `docs/install.md` rather than fixed. Stable and Preview use different CLSIDs.
