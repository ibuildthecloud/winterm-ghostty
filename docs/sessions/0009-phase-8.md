## KD-06 — a ligature's second half blinks with the cursor

Reported from use: type `--` at a prompt, move the cursor back onto the **first** dash,
and the **second** dash blinks in antiphase with the block cursor.

### What was measured

Frames of a live pane captured with `harness/wgc-shot`, diffed per pixel. Cells are
13 px wide, column 0 starts at x=18, so one cell is 338 px of 13x26.

| line | cursor parked on | pixels changing per blink |
|---|---|---|
| `--` | first dash | **365 px, x=[239..261] — two cells** |
| `--` | second dash | 331 px — one cell |
| `xy` | first letter | 338 px — one cell |

Only the first case leaks past the cursor's own cell, and only on the three pixel rows
carrying the dash's ink. A glyph disappearing, not a rectangle painting over one.

### Cause

ghostty breaks shaping runs at the cursor (`font/shaper/run.zig:178`) so a ligature under
the cursor is split into its components. That break is only applied when the row is
re-shaped, and `renderer/generic.zig:2408-2410` re-shapes a row only when it is dirty:

```zig
if (!rebuild) {
    if (!dirty.*) continue;
```

Moving the cursor changes no cell contents, so the row is never re-shaped. The `--` keeps
the ligature shaping it was given while the cursor was still to its right — one glyph,
owned by the first cell, spanning two — and drawing the cursor block over that cell takes
the ligature's right half with it.

### Confirmed, not merely argued

`FontShapingBreak.cursor` was temporarily defaulted to `false`, libghostty rebuilt and
deployed. That knob **disables** the break, so it predicts the symptom becomes universal
— including in the write-and-move-in-one-burst case that renders correctly today.
Predicting a change in a case that *works* is a sharper test than watching a symptom
vanish.

| case | break on | break off |
|---|---|---|
| `…q--`, cursor on first dash | 338 px — correct | **365 px, identical range to the bug** |
| `…qxy`, cursor on the `x` | 338 px | 338 px — unchanged |

Reverted afterwards and re-measured back to 338 px, which is what confirms the revert —
not a file hash, since the previously deployed DLL predated current HEAD anyway.

### Method note worth keeping

**Four printf-based repro attempts failed before the mechanism was clear**, and the
reason is general: writing the text and the cursor movement in one burst means the
renderer's *first* shaping of that row already has the cursor in place, so nothing is
stale. Inserting a pause reproduces it with no shell, no readline and no typing. Any
repro that emits content and cursor movement together will report this defect as absent.

Also cost real time: four capture runs went to the wrong profile. The default profile is
**"Ubuntu"** (`{51855cb2-…}`, `cursorShape: filledBox`); `Ubuntu-24.04` is a different,
hidden, auto-generated profile with no cursorShape, which is why every attempt showed a
bar cursor and no block to blink.

## Packaging

### The decision the plan flagged, resolved

Phase 8's open question — "signing/identity for the MSIX (test cert vs proper
identity)" — was put to the gate and answered: **self-signed certificate**, package
identity `WintermGhostty`, display name "Windows Terminal (ghostty)", publisher
`CN=Darren Shepherd`.

The identity change was not optional, for three independent reasons:

1. An MSIX signature is valid only when the certificate subject matches `Publisher`
   exactly. Upstream's `CN=Microsoft Corporation, …` is unsignable by anyone else.
2. It would ship an artifact identifying itself as Microsoft's.
3. `Name` forms the package family, so `WindowsTerminalDev` would have **replaced** a
   real Windows Terminal Dev install rather than sitting beside one.

The execution alias moved to `wtg.exe` for a related reason: an alias is machine-global,
and claiming `wtd.exe` would take it from a Dev install — precisely this audience. Zero
references to the alias existed in this repo, so the rename cost nothing here.

### What was built

- **terminal patch 45** — manifest identity, branding strings, alias; `WtExeUtils.h`
  follows both halves (`WtdExe` → `wtg.exe`, `IsDevBuild()` matches the new name), else
  the shell extension resolves a path that does not exist and "Open in Terminal" breaks
  silently.
- **`scripts/package.ps1`** — builds, signs and stages `dist/`: the `.msix`, the `.cer`,
  the `Microsoft.UI.Xaml.2.8` framework package, and `SHA256SUMS.txt`.
- **`docs/install.md`** — install, engine opt-in, and two things a download page usually
  skips: what trusting a self-signed certificate actually grants, and the CLSID conflict
  below.
- **[v0.1.0](https://github.com/ibuildthecloud/winterm-ghostty/releases/tag/v0.1.0)** —
  published, four assets, 38.5 MB package.

Two traps encoded in the script rather than in a comment somewhere:

- `signtool verify` reports an untrusted chain for a self-signed package. That is
  correct behaviour, so it is swallowed deliberately — left in `$LASTEXITCODE` it makes
  a good packaging run look failed.
- The WinUI framework package ships even though most machines have it, because when it
  is missing `Add-AppxPackage` fails with a bare `0x80073CF3` naming no dependency.

Also learned: `Executable` in the appExecutionAlias extension names a file **inside the
package**, and MakeAppx rejects one that is not there. Only `Alias` is the global name,
and the two need not match.

### Not verified

**Nobody has installed the artifact.** The session had no elevation, so importing the
certificate into `LocalMachine\TrustedPeople` and running `Add-AppxPackage` were never
executed. The package is signed, timestamped and structurally valid, and its identity was
read back out of the built `.msix` rather than assumed — but "it installs" is untested,
and the release is public. First thing to check next session, or by hand:

```powershell
# elevated
Import-Certificate -FilePath .\winterm-ghostty-0.1.0.0.cer -CertStoreLocation Cert:\LocalMachine\TrustedPeople
# not elevated
Add-AppxPackage -Path .\winterm-ghostty-0.1.0.0-x64.msix -DependencyPath .\Microsoft.UI.Xaml.2.8.appx
```

### Known limitation shipped knowingly

The COM class IDs for the shell extension, the "Open in Terminal" verb and
default-terminal handoff are inherited unchanged from upstream. A machine with Windows
Terminal **Dev** installed will have two packages registering the same CLSIDs, and the
last to register wins. Changing them means changing them in C++ too, so it was recorded
in `docs/install.md` rather than fixed. Stable and Preview use different CLSIDs.

## Second half: CI, a portable distribution, and v0.2.0

The gate directed that releases be produced by a GitHub Action rather than this
laptop, and asked for the dev/production channel split.

### Channels, and eight fresh CLSIDs (terminal patch 46)

Patch 45 had shipped by hijacking the Dev manifest, so the local build and the
released build were one identity - installing a release replaced the thing you
develop against. Upstream already has the machinery: four brandings selected by
`WindowsTerminalBranding`, each with its own manifest, alias and CLSID triple.

| | identity | alias | manifest |
|---|---|---|---|
| shipped | `WintermGhostty` | `wtg.exe` | `Package.appxmanifest` |
| local | `WintermGhosttyDev` | `wtgd.exe` | `Package-Dev.appxmanifest` |

**Eight GUIDs were regenerated** - console handoff, terminal handoff, shell
extension and proxy stub, per channel. That is the substantive half: COM
registrations are machine-global, and moving the shipped build to Release
branding *without* regenerating would have moved the collision from Windows
Terminal Dev, a niche install, to Windows Terminal stable, which is everywhere.
The first three exist twice each - manifest and a C++ header selecting on
`WT_BRANDING_*` - and both copies must agree. `IsDevBuild()` has to match on
`WintermGhosttyDev`, since `WintermGhostty` is a prefix of it.

### The workflow found three latent defects, and none were CI's fault

Six runs. Two failures were mine (PowerShell argument binding, twice - a `/p:`
argument landing on `-Platform`, then an array splat passing positionally).
**Three were real defects in this repository, and none could surface on a machine
that had built before:**

| defect | hidden locally by |
|---|---|
| NuGet restored against nuget.org, never the repo's own `TerminalDependencies` feed - so Taef, PGO-Helpers and ThemeHelpers resolved nowhere | an already-populated `terminal\packages` |
| `ITerminalHandoff.h` missing: README's Release sequence is three msbuild invocations and only the last was run | a `bin\` already containing the generated header |
| `winrt/Microsoft.Terminal.Settings.Model.h` missing: `TerminalSettingsAppAdapterLib` consumes four winmds through bare `<Reference><HintPath>` rather than `<ProjectReference>`, so nothing orders it after their producers | a `bin\` already containing the projections |

The last is an upstream ordering hazard, not a missing step; the fix builds the
winmd producers explicitly, since the edge cannot be added from outside the
vcxproj files. **README.md's Release sequence is correct locally and insufficient
on a clean tree** - worth fixing there too.

That is the reproducibility claim being tested rather than asserted. It was not
true before this session.

### Portable, and a correction

I had reported portable as blocked, on a measured `0xC0000409` crash. **That was
wrong, and the measurement was of the wrong thing.** I had copied `bin\` and
dropped a `.portable` marker beside it. Upstream ships
`build/scripts/New-UnpackagedTerminalDistribution.ps1` precisely because the
layout is more than that: `Microsoft.UI.Xaml.dll` and its resources must be
copied in from the framework package, and `resources.pri` must be *merged* with
XAML's. `scripts/package-portable.ps1` wraps it.

Verified against the published artifact rather than a local rebuild: downloaded
the release asset, checksum matched, launched it, and `defaults.json` appeared
beside the exe - so the marker works and nothing lands in `%LOCALAPPDATA%`.

**This also answers the certificate question properly.** Developer Mode does not
permit installing an unsigned MSIX: `Add-AppxPackage -AllowUnsigned` returns
`0x80073D2C, publisher is not in the unsigned namespace`, and a manifest carrying
that namespace's marker OID could no longer match a certificate subject, so it
could not be signed either. MSIX always wants a signature. The way to avoid one
is to not use MSIX.

### v0.2.0

Built and published entirely by the workflow. **Portable ZIP only** - no signing
secret is configured, and an unsigned MSIX is never attached to a release
because publishing something nobody can install is publishing a trap. The tag
path used to fail outright in that state; that was right when the MSIX was the
only artifact and is not right now.

### Still open

- **Signing.** The certificate exists only in this machine's `CurrentUser\My`,
  with no `.pfx` backup, and no repository secret. Until one exists, releases are
  portable-only. Whether a private signing key belongs in GitHub secrets is a

- **The MSIX install path remains unverified.** Nobody has trusted the

- `terminal/packages.bak` is still on disk from reproducing the NuGet failure.

## Third stretch: three defects found by using it, and two more releases

v0.2.0 was published on a "does it launch" check. The user hit a crash on their
first real interaction with it. Everything below follows from that.

### KD-07 — the shipped build crashed on ctrl+= (fixed, v0.2.1)

`STATUS_STACK_OVERFLOW` inside libghostty. **Cause: `WindowsTerminal.exe`
linked with MSVC's default 1 MB stack reserve while Zig-built code assumes
16 MiB**, and a DLL has no stack of its own - its PE `SizeOfStackReserve` is
ignored, so a synchronous call from a WT-owned thread runs on that thread's
stack. The fourth instance of PLAN.md's 2026-08-04 note. Fixed by reserving
16 MB in the exe rather than wrapping another call site, because:

| exe stack | control DLL | result |
|---|---|---|
| 1 MB | stock | crash, zoom 11 |
| 1 MB | `set_size` wrapped in `RunWithEngineStack` | crash, zoom 12-13 |
| 16 MB | wrapped | passes |
| 16 MB | stock | passes |

Wrapping the most plausible call site did not fix it, and the path that
actually overflows is still unidentified. That is the argument against the
opt-in wrapper: it has now been forgotten four times, and forgetting produces a
crash on someone else's machine.

**A CPU-target theory was built, supported, and wrong.** The CI build crashed
where a local build of the same commit did not, and a `-Dcpu=baseline` local
build crashed too. The surviving runs turned out to be **cascadia panes**. The
pin stays - an artifact should not depend on who built it - but it is not the
fix and is no longer recorded as one.

### KD-08 — `?` arrived as `/` (fixed, v0.2.2)

`consumed_mods` was hardcoded to `GHOSTTY_MODS_NONE`. ghostty computes
`effectiveMods() = mods.unset(consumed_mods)` and only sends text directly when
that is empty, so `?` looked like `shift+<something>`, skipped the text branch,
and encoded `CSI 47;2u` - the *unshifted* codepoint, `/`, plus shift. Only
applications enabling the kitty protocol reached that encoder, which is why it
presented as one misbehaving program.

The clarification that did it: "`?` prints `/`" rather than "`?` is missing". A
key arriving with its shift lost is a different defect from a key being dropped,
and the first hypothesis was the second one.

### KD-06 — the ligature blink (fixed, v0.2.2)

Cursor movement dirties no row, so a row kept the shaping it had when the cursor
was elsewhere. 365 px across two cells before, 338 px - one cell - after. Both
halves are upstream code and no cursor movement marks a row dirty upstream
either, so it should reproduce on native ghostty; recorded as inference because
no native build was run.

### The gate that certified the wrong thing

`scripts/smoke-release.ps1` exists because "it launched" let v0.2.0 out. Writing
it produced three failures worth keeping, all of which made it *pass* things it
should have failed:

1. Setting only `profiles.defaults.engine` did not produce a ghostty pane. Three
   consecutive passes were cascadia.
2. `AdjustFontSize` is a no-op on a ghostty pane, so **a visibly zooming pane is
   evidence of cascadia** - the screenshots showed exactly that and I read them
   as success.
3. The engine assertion listened on DBWIN but discarded the pid in the first
   four bytes. DBWIN is machine-global, so it proved the engine using traces
   from the developer's *other* terminal.

It now writes an explicit profile, asserts a `[ghostty]` trace **from the
process under test** on every run, dumps the engine's last activity on failure,
and reports a disconnected session rather than blaming focus.

### Releases

- **v0.2.0** withdrawn (tag kept) - shipped the KD-07 crash.
- **v0.2.1** - stack fix. Published asset downloaded, checksummed, and smoke-run.
- **v0.2.2** - `?` and the ligature blink. Checksum verified; the interaction half

Also: the MSIX left the release notes (it is built but never published, since an
unsigned one cannot be installed), and `SHA256SUMS.txt` moved to LF - CRLF made

to ignore checksums.

### The recurring lesson

Three separate times a measurement said something confident and wrong, and each
time the thing that caught it was a **control run**: kitty-mode captured zero
bytes and read as "the key is dropped" until legacy mode captured zero bytes
too; the CPU-target table collapsed when the "passing" configuration turned out
to be cascadia; the first KD-06 verdict measured mouse movement at the window
edge because the pane had no cursor drawn.
