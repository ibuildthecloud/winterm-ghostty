## 1. Outcome

**The Windows Terminal integration primitive works.** libghostty renders into a
DirectComposition surface handle, and that handle is bound into a **system-XAML**
`SwapChainPanel` with `ISwapChainPanelNative2::SetSwapChainHandle` — byte-for-byte the call
Windows Terminal already makes in `TermControl::_AttachDxgiSwapChainToXaml`.

Phase 5 therefore does not need to add an attach path to WT. It needs to supply a handle to
one that already exists.

Both exit criteria are met, and the device-loss test returned something better than a pass:
it **converted an inference into a measurement**.

## 2. Exit criteria

- [x] **Clear-colour in a SwapChainPanel; live resize with no stretch artifacts;
      per-monitor DPI change handled.**

      | Check | Measured |
      |---|---|
      | Panel contents | `#282C34` — libghostty's configured background |
      | Live resize | uniform across 540×430 → 1400×900, grow and shrink |
      | Composition scale | `CompositionScale 1.50 x 1.50` delivered to the surface |
      | Driver | `driver=hardware feature_level=11_1` |

      **Deviation on "animated":** the clear colour is static, because the animation would
      have to come from the `bg_color` pipeline that Phase 3 owns. What the criterion was
      really after — proof that frames keep being presented rather than one lucky
      composite — is instead evidenced by the resize and device-loss sequences, both of
      which show the panel tracking new content live. Recorded as unmet-as-worded rather
      than quietly reinterpreted; see §4 deviation 1.

- [x] **Kill the device → surface recovers without app restart.**

      ```
      bound swap chain handle 000000000000179C
      simulating device loss (frame 3)
      rebuilding device after loss (1002x584)
      D3D11 device ready: driver=hardware feature_level=11_1 size=1002x584
      device rebuilt: driver=hardware
      swap chain changed, re-attaching
      bound swap chain handle 00000000000021D0
      ```

      The process never restarted and the panel still renders `#282C34` afterwards. Note
      the rebuild used `1002x584` — the *current* size, not the creation size — so resize
      state survives recovery.

## 4. Deviations

| # | Deviation | Reason |
|---|---|---|
| 1 | The clear colour is **static**, not animated. | Animation belongs to the `bg_color` pipeline, which is Phase 3's. Rather than bolt a fake animation onto the skeleton purely to satisfy the wording, liveness is evidenced by resize and device-loss both updating the panel. Flagged rather than reinterpreted. |
| 2 | **Added a `swap_chain_changed` apprt action** — a public C API addition, beyond Phase 2's listed scope. | The device-loss exit criterion is unreachable without it: a getter cannot tell an embedder its handle went stale, so the panel would sit on a dead surface showing a frozen frame. Followed the documented procedure in `action.zig` (append to the end of `Key` for ABI compatibility, mirror into `ghostty.h`); the existing `checkGhosttyHEnum` test verifies the two stay positionally in sync. |
| 3 | Device loss is **simulated** via `GHOSTTY_D3D11_SIMULATE_DEVICE_LOSS`, not induced. | D3D11 has no equivalent of `ID3D12Device::RemoveDevice`, and provoking a genuine TDR means hanging the GPU. The hook forces *our* recovery path deterministically. It does not reproduce a real TDR's invalidation of driver state, and the code says so. |
| 4 | The harness is **unpackaged**, unlike WT. | Needed an application manifest to work at all (learning 1). Packaged identity would have hidden that requirement rather than surfaced it. |
| 5 | `Device.recreate` re-walks the whole hardware→WARP ladder instead of pinning the previous rasterizer. | A device can be lost precisely *because* the hardware went away — eGPU unplugged, driver uninstalled. Retrying the same rasterizer would fail forever; falling to WARP is the correct outcome. |

## 6. Learnings for the plan

1. **Unpackaged XAML Islands needs a `<maxversiontested>` application manifest.**
   `WindowsXamlManager::InitializeForCurrentThread()` otherwise fails with `E_UNEXPECTED`,
   and C++/WinRT fail-fasts (`0xC0000409`) with **no message at all** unless the
   `winrt::hresult_error` is caught — at which point the message is perfectly explicit.
   Any future unpackaged harness needs both the manifest and a top-level catch.
2. **No NuGet is required for system XAML.** The Windows SDK ships 345 C++/WinRT headers
   including `Windows.UI.Xaml.Hosting`, and `ISwapChainPanelNative2` lives in
   `windows.ui.xaml.media.dxinterop.h`. The harness builds with `cl` plus the SDK, same as
   the others. This matters for Phase 5 too — WT already restores CppWinRT via NuGet, so
   there is no new dependency to introduce.
3. **A new handle after device loss is now measured, not inferred.** `0x179C → 0x21D0`.
   Phase 5 must wire `swap_chain_changed` into WT's `SwapChainChanged`; treating the handle
   as stable would produce a frozen pane that looks like a hang.
4. **The two presentation modes have different size authorities**, and this is a permanent
   asymmetry rather than a Phase 1 shortcut: a window knows its own size, a composition
   surface is only ever what the embedder says it is. `drawFrameStart` now branches on the
   mode.
5. **`ResizeBuffers` does not invalidate the composition handle** — the panel references the
   handle, not the swap chain. So resize needs no re-attach, and only device loss does.
   Worth stating because the opposite assumption would add a pointless re-bind per resize
   in Phase 5.
6. **Phase 5's attach path already exists in WT.** `_AttachDxgiSwapChainToXaml` takes a
   `HANDLE` and `ControlCore` already duplicates it and raises `SwapChainChanged`. The
   integration is supplying a handle from a different producer, not building new plumbing —
   which is a meaningfully smaller and more upstreamable change than the plan assumed.

## 7. Next-phase readiness gaps (Phase 3 — real terminal rendering)

- **Phase 3 inherits two `phase1_skeleton` markers**, both of which must go: `RenderPass.step`
  ignoring draw steps, and `Frame.skeletonClear` substituting the background colour. The
  second one is load-bearing for the current demos — removing it before pipelines work
  would return the harness to a black window.
- **The shader-toolchain sub-question is still open** and should be settled at readiness,
  not during the phase: hand-port the shader set to SM 5.0 (what #11886 did for one
  pipeline) versus routing ghostty's glslang→SPIRV-Cross output to HLSL compiled with
  `fxc`. Phase 0 established the target is `fxc`/SM 5.0 DXBC either way.
- **`shadertoy.Target.hlsl` currently returns an error.** That is fine until Phase 6, but
  Phase 3 should confirm nothing in the normal (non-custom-shader) path reaches it.
- **Premultiplied alpha is now live in composition mode but untested against real content.**
  Blending errors would first appear when actual glyphs are drawn, i.e. in Phase 3, not
  here — a uniform clear cannot reveal them.
- **The atlas upload path is written but unexercised.** `Texture.replaceRegion` uses
  `UpdateSubresource` and has never run, because nothing has built a glyph atlas yet.
