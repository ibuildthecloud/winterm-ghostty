## 1. Outcome

**libghostty renders to the screen on Windows.** `harness/hwnd-host` drives the embedded C
API to put a D3D11-backed surface in a window that clears to the terminal's own configured
background colour, resizes cleanly, is DPI-correct, and behaves identically on the hardware
GPU and on the WARP software rasterizer.

The `windows` branch is a four-patch series on the Phase-0 pin, exported to
`ghostty-patches/`, and Windows now has a real GPU backend for the first time —
`renderer=renderer.generic.Renderer(renderer.D3D11)`, with `d3d11.dll` in the DLL's import
table.

## 4. Deviations

| # | Deviation | Reason |
|---|---|---|
| 1 | The `d3d11-backend` patch is **not** a thin skeleton. It is ~1,900 lines across 12 files. | PLAN called it a skeleton, but `GenericRenderer(D3D11)` only compiles if the *entire* `GraphicsAPI` surface exists — `Target`, `Frame`, `RenderPass`, `Buffer`, `Sampler`, `Texture`, `shaders`, plus ~25 methods. Stubbing the bodies does not shrink the type surface. Raised with the gate mid-phase, who chose to push through rather than defer. |
| 2 | `phase1_skeleton` markers exist in **two** places, not one. | `RenderPass.step` ignores draw steps (expected). But `generic.zig` clears to *transparent black* and paints the background with the `bg_color` **pipeline**, so stubbing steps left a black window — indistinguishable from a broken swap chain, and worthless as a demonstration. The second marker clears to the terminal background instead, taken from the same uniforms the shader would read. Both must go in Phase 3. |
| 3 | Patch 4 was **amended** rather than extended with a fifth commit. | Three bugs found by running the harness are all part of the same topic ("the D3D11 backend"); ADR 0004 wants one commit per topic, and the branch is local-only, so amending is the clean option. |
| 4 | The appcontainer probe did **not** build a trivial packaged app, as PLAN specified. | Inspecting WT's own manifest answered the question outright and more authoritatively: it declares `runFullTrust` + `Windows.FullTrustApplication`, so nothing loaded into it is appcontainer-restricted. Building a *different* packaged app would have measured a constraint that does not apply to the one host we care about. The import table was enumerated anyway (§6 learning 4) so the answer is evidence-based rather than inferred. |
| 5 | Harvested files carry attribution headers that also record *what the harvest lacked*. | The per-file-note convention was ratified at the Phase 0 retro. The extra detail is because #11886 left most vtable slots as `Reserved`; a future reader hitting one needs to know it is an unwired stub, not an unsupported API. |
| 6 | Added `hlsl` to `shadertoy.Target` with a conversion that returns an error. | Needed for `custom_shader_target` to compile. SPIRV-Cross has an HLSL backend, so Phase 6 is wiring rather than missing capability — and refusing beats silently dropping a user's shader. |

## 5. Decisions needed

### DECISION-NEEDED 1 — ARM64 is blocked by a Zig 0.16.0 stdlib bug

`zig build -Dapp-runtime=none -Dtarget=aarch64-windows-msvc` fails in **Zig's own standard
library**, not in ghostty and not in our patches:

```
lib\std\debug\SelfInfo\Windows.zig:670:9: error: @ptrCast increases pointer alignment
error: sub-compilation of libubsan failed
```

The site is `getNtdllProc`, which `@ptrCast`s the `*anyopaque` returned by `loadNtdllProc`
to a function pointer. On aarch64 function pointers require 4-byte alignment where x86_64
requires 1, so the cast increases alignment and Zig rejects it. It needs an `@alignCast`.

Scope check: a trivial Zig program cross-compiles to `aarch64-windows-msvc` cleanly, so
this is not a blanket toolchain failure — it is reached via `std.debug`'s self-info path
(and via `libubsan`, which ghostty's C dependencies pull in).

**Recommendation:** report it upstream to Zig and, in the meantime, decide between three
options at the retro — (a) accept ARM64 as deferred until a Zig release fixes it, (b) pin a
newer Zig once one ships the fix (a pin change is a readiness/retro decision per AGENTS.md),
or (c) carry a local stdlib patch, which is the worst option since it is invisible to
`ghostty-patches/` and would silently rot. Recommend (a) with (b) at the next pin bump:
nothing before Phase 8 needs ARM64, so this blocks no downstream work today.

## 6. Learnings for the plan

1. **Embedders must raise the stack above MSVC's 1 MB default — but only just.**
   Bisected after the fact, because the first write-up of this overstated it:

   | `/STACK` | Result |
   |---|---|
   | 1024 KB (MSVC default) | `STATUS_STACK_OVERFLOW` |
   | 2048 KB | OK |
   | 4096 / 8192 KB | OK |

   So the requirement is *just above* 1 MB, not enormous. The harness uses 16 MB anyway
   for two reasons: it is the budget Zig itself assumes (Zig-built exes carry a 16 MiB
   stack reserve in the PE header, and `std.Thread.default_stack_size` is 16 MiB — MSVC's
   1 MB is the outlier), and 2 MB only passed the paths this harness exercises. The
   failure mode is a bare `STATUS_STACK_OVERFLOW` with no diagnostic whatsoever, which is
   what makes thin headroom a bad trade.

   Measured against a **Debug** libghostty; a Release build may fit in 1 MB — untested.
   **Phase 5 should check this in Windows Terminal** rather than assume either way.
2. **The ghostty build emits no import library** for `ghostty-internal.dll` (only for
   libghostty-vt). The harness synthesizes one via `dumpbin` → `.def` → `lib`. Phase 5
   needs the same, or an upstream build change. The `LIBRARY` line in the `.def` is
   load-bearing: without it the exe searches for the wrong DLL name and dies at load.
3. **`GHOSTTY_LOG=1` gates all of ghostty's stderr logging.** Without it a failing embedder
   sees nothing at all. Any future debugging session should set it first.
4. **libghostty imports ntdll directly** (~40 `Nt*`/`Ldr*` functions) because Zig's stdlib
   targets the native API. Harmless under WT's full-trust package, but it permanently rules
   out any appcontainer-restricted host, and it is not fixable at our layer.
5. **#11886's value is narrower than "the D3D11 base".** Its COM/DXGI/D3D11 bindings are
   genuinely reusable, but it wired only the vtable slots its SwapChainPanel demo called;
   six more slots and five descriptor types had to be added for a renderer. Its
   `device.zig` was not reusable at all. DESIGN's harvest map should say "COM/DXGI/D3D11
   bindings" rather than "D3D11 module base".
6. **Phase 3 is larger than its PLAN text implies.** It inherits an empty
   `PipelineCollection`, no HLSL, and no atlas draw path — plus removing two
   `phase1_skeleton` markers. The shader-toolchain sub-question (hand-port to SM 5.0 vs
   route glslang→SPIRV-Cross→HLSL) should be settled at its readiness step, not during it.

## 7. Next-phase readiness gaps (Phase 2 — SwapChainPanel proof)

- **Composition mode is stubbed, deliberately.** `Device.init` returns
  `error.Unsupported` for it and `ghostty_surface_get_swap_chain_handle` returns null.
  The `platform-win32` C API and the `Target` union already carry the mode, so Phase 2 is
  filling in `CreateSwapChainForCompositionSurfaceHandle` rather than reshaping anything.
- **`syncToWindow` does not apply to composition mode** — there is no window to query.
  Phase 2 must drive resize from the embedder's explicit call, and its open question about
  device-lost re-attach semantics is now concrete: the handle is re-read after recreation,
  which is exactly the case `ghostty_surface_get_swap_chain_handle`'s doc comment warns
  about.
- **Phase 2's harness-stack question (WinUI 3 vs system XAML) is still open** and is the
  one that matters beyond the harness, since the `ISwapChainPanelNative2` IIDs differ
  between the two stacks and Phase 5 needs the system-XAML variant.
- **`DXGI_ALPHA_MODE` differs by mode** — `IGNORE` for hwnd, `PREMULTIPLIED` for
  composition. Already encoded in `device.zig`, but Phase 2 is where the premultiplied path
  is first actually exercised, so blending errors will surface there.
