# Session 0008 — Phase 7 (presentation & performance)

2026-08-06 / 2026-08-07. First sitting of Phase 7, run interactively with the user at
the machine rather than unattended.

Two things came out of it: the pane's throughput problem is one line of code, and `?`
could not be typed into a ghostty pane.

---

## 1. Throughput: the forced render was the whole gap

The Phase 3 number everyone had been carrying — "2.9x slower than Windows Terminal" —
measured `harness/hwnd-host`, not a pane. The pane is what a user has, so the first job
was to measure the pane.

It was worse than the harness: **4.2 MB/s against cascadia's 38.1**.

The cause was `GhosttyControlCore::_connectionOutputHandler`, which called
`ghostty_surface_render_now` for **every chunk of pty output**. That call exists for a
real reason — Phase 5's repaint freeze, where libghostty's coalescing wakeup could fold a
notify into a wake that had already sampled state, and the last batch never reached the
screen — but forcing a synchronous render per chunk means a 64 KiB `cat` renders hundreds
of times to show one final frame.

Replacing it with a `til::throttled_func` (8 ms, trailing-only, no debounce) took the pane
to **28.0 MB/s median**. `docs/perf/throughput.md` carries the numbers and the method; the
old 2.9x section is marked superseded rather than deleted, because its method and its
detached-vs-connected finding still stand.

The remaining ~25% is not a throttle problem. It needs libghostty to re-arm its wakeup
correctly so the forced render can go away entirely, which is an upstream change and is
recorded as such, not attempted here.

### Three measurements were wrong before one was right

Worth writing down, because each looked convincing:

1. **Other GPU load moved the harness result 15.2 → 12.3 MB/s** between two runs of the
   same binary. Benchmarks on this machine need the machine quiet, and a single run
   proves nothing.
2. **`profiles.defaults.engine` was already `ghostty`**, so a "cascadia vs ghostty"
   comparison measured ghostty twice and reported them as different engines. The user
   caught this, not the harness.
3. **"Everything was Debug on both sides" was asserted and was false** — Phase 3's 14.9
   MB/s was already a ReleaseFast build. A claim about build configuration is checkable
   in seconds and was not checked.

## 2. `?` could not be typed into a ghostty pane

Reported by the user as "I can't seem to type ?". It came out as `/`, and under any real
typing speed the damage spread well past that one key: typing `echo A?B/C` quickly into a
ghostty pane produced

```
????ECH?O A??B?C
```

with Shift smeared onto neighbouring keys. The same keystrokes, the same window, a
**cascadia** pane: `echo A?B/C`, exactly right.

### The engine was not at fault, and proving that came first

`ghostty_surface_key` had to be cleared before Windows Terminal could be blamed, so
`harness/hwnd-host` gained `GHOSTTY_HARNESS_KEY=<chars>`: it synthesizes the key event a
real keystroke for a character would produce — scan code, mods, text, unshifted codepoint
— hands it to libghostty, and the pty trace says what came out. Given the right event,
`?` encodes to a clean `0x3f`.

```
[hwnd-host] key U+003F scan=0x35 mods=0x1 consumed=0x0 text="?" unshifted=U+002F
[extpty] write 1 bytes to child: 3f
```

`consumed_mods` being hard-coded to `GHOSTTY_MODS_NONE` had been the leading suspect,
reasoned from `key.zig`'s `effectiveMods()`. It is not the cause: `key_encode.zig`'s
legacy path writes the utf8 through regardless, and fixterms already discounts Shift when
the shifted and unshifted codepoints differ. Reading the source produced a plausible
wrong answer; the probe produced the right one in one run.

### The cause

`TrySendKeyEvent` asked **`GetKeyboardState()`** for the keyboard state to translate the
key under. That reports the state as of the last message the *calling thread* retrieved,
and XAML raises `KeyDown` as a routed event some way behind its message pump — so under
real typing speed the snapshot has already moved on. Shift arriving early or leaving late
is enough to pick the wrong character out of the layout.

A cascadia pane is immune for a structural reason, not by luck: it never calls
`ToUnicode` at all. Its text arrives as `CharacterReceived`, which Windows generated at
`TranslateMessage` time with the correct state.

The fix is to translate under the modifiers that came **with the event**, which cannot
drift from it. The translation moved to `GhosttyKeyTranslator` — next to the two other
rules learned the same way — where it is a pure function of `(modifiers, vkey, scanCode)`
and reachable from a unit test. The unshifted codepoint falls out as the same call with
no modifiers at all, which deleted the hand-cleared copy of the state array.

### How it was verified

Nobody was at the keyboard for most of this, so:

- A launcher script opens a dev-build window, forces focus, types with `SendKeys` and
  photographs the pane with `harness/wgc-shot`. Reading the pane from a screenshot beats
  every indirect channel tried first — a file the shell writes, a window title — because
  it shows what a human would see, including the shell's own error messages.
- **Typing speed is a variable, not a nuisance.** At 200 ms/character the ghostty pane was
  already correct *before* the fix. Only the burst reproduced it. A test that types slowly
  would have reported the bug fixed while it was not.
- The control that settled it: the Command Prompt profile was temporarily set to
  `"engine": "cascadia"`, given the identical burst, and came out perfect. Settings
  restored afterwards.
- After the fix, the burst produced `echo Ab?Cd/Ef:Gh;Ij<Kl>Mn_Op-Qr` character for
  character.

The pane under test was on the ghostty engine, and that is a fact rather than an
assumption: `ghostty-internal.dll` and `d3d11.dll` are loaded in the process, and the only
file changed was `GhosttyControlCore.cpp`, which a cascadia pane never executes.

### Cover added

- `GhosttyKeyTests::ShiftComesFromTheEventNotTheThread` — **fails against the old code for
  the reason the bug existed**: no key is held while a unit test runs, so a
  `GetKeyboardState` implementation sees Shift up and answers `/`. Skips off a US layout,
  since the mapping being asserted is the layout's and not ours.
- `smoke-harness.ps1` check 2b — `?/aA` through `ghostty_surface_key`, asserting the exact
  bytes that reach the child. This covers the half of the problem this repo owns; it could
  not have caught the actual bug, and the report says so rather than implying otherwise.

### A possible loose end from Phase 3

PLAN.md carries "the occasional wrong character from the synthetic input driver,
unattributed" out of Phase 3, deferred into this phase. It is the same *shape* as this
bug and may be the same cause, but the harness dispatches key messages straight from its
own message loop — where `GetKeyboardState` is in sync with the message being handled — so
the mechanism does not obviously transfer. Left open, not claimed closed.

## 4. The repaint the throttle put at risk

The throttle replaced the Phase 5 freeze workaround, so the freeze was the thing to check
before anything else. `docs/manual-validation.md` item 1, driven rather than hand-run:
`dir /s C:\Windows\System32` followed by a marker echo, photographed at 3 s and 8 s with
no scroll, resize or keystroke in between.

At 3 s the pane is mid-scroll and moving. At 8 s it is complete — 25,005 files, the
marker, and the prompt back. **The last batch reaching the screen is the whole
assertion**: the freeze's signature is precisely that it does not, and that the pane sits
stale until something unrelated forces a render.

Passes. **The unfocused half is still unchecked**, and that is the half the original bug
needed — it was found in a pane that was not focused. That one still wants a human.

## 5. Phase 7 readiness

`docs/phase-7-readiness.md` answers the three open questions against source. The three
findings worth repeating here:

**One of the open question's own options does not exist.** It asks whether the
waitable-swapchain wait should live in "an xev async bridge, a dedicated wait thread, or
timer-approximation". libxev cannot wait on a Win32 event handle at all: `associate_fd` is
`CreateIoCompletionPort`, which does not accept an auto-reset event, and there is no
`RegisterWaitForSingleObject` anywhere in the pinned dependency. Meanwhile cascadia
answers the same question **in this tree** without an event loop — waitable flag,
`SetMaximumFrameLatency(1)`, and a plain blocking `WaitForSingleObjectEx` on the render
thread, guarded against the auto-reset double-wait.

**An exit criterion is unmeetable as written.** "Idle ghostty pane: 0 presents/sec with
cursor blinking" is a contradiction — a visible blink changes pixels and changed pixels
need a present. The restatement that matches what cascadia does is written up as a
DECISION-NEEDED rather than adopted.

**And the idle behaviour is worse than the criterion assumed.** A blink currently costs a
full rebuild and a full-surface present every 600 ms on a completely idle pane, because
`rebuildCells` sets `cells_rebuilt = true` unconditionally and that flag alone drives
`needs_redraw`. Row-level dirty tracking already exists and gates rebuild work, never
presentation. Making that flag honest is the cheapest item in the phase.

## 6. Second sitting — a pty bug, a chased ghost, and the first real measurement

**The child was told the wrong terminal size.** A ghostty pane reported `18 56`
to `stty size` while being 109x27, and had done since Phase 5. `ConptyConnection::Resize`
only reaches the pseudoconsole while the connection is `Connected`, but `Start()`
creates the pseudoconsole *before* reaching that state — and TermControl
initializes the core (which sizes the surface, which fires `resize_pty`) before
starting the connection. The correct size was computed every time and applied to
nothing. The core now replays it on `Connected`. Verified: `27 109`.

It was **visible in every screenshot taken that day** — commands wrapping at
column 56 in a 109-column window — and went unread. Nothing had ever asked the
child how big it thought it was; that is now manual-validation step 1b.

**A reported "skewed image" was chased to the wrong conclusion twice** before
measurement settled it. Recorded in `docs/known-defects.md` as KD-01/KD-03. The
short version: our image geometry is correct (three placements measured against
their requested cell boxes), kitty stretches `c`+`r` exactly as ghostty does
(checked against kitty's `update_dest_rect`, not its prose), and the distortion
was chafa 1.14.0 — which cannot ask the terminal anything, because the pty
carries no pixel dimensions (`ws_xpixel=0`, a ConPTY property no Windows
terminal can change) and 1.14 has no `--probe`. chafa 1.18.2 probes, and the
plain invocation then renders at ink aspect 0.969 against a 0.969 ground truth.

That the probe works is a check on us too: the queries travel pane → ConPTY →
WSL and the replies come back correctly.

**The mistake worth keeping:** this entry was briefly closed as "not a defect" on
the strength of a logo *looking* right. It took two rounds of user pushback to
reopen. Every other conclusion in this session came from a measurement; that one
did not, and it was the one that was wrong.

## 7. Phase 7 begins: the idle present rate, measured

Patch 32 adds `GHOSTTY_D3D11_PRESENT_RATE=1`, because the idle criterion asks
about something invisible — a surface presenting the same pixels repeatedly
looks identical to one presenting nothing.

First measurement, `hwnd-host` idle, ReleaseFast, hardware driver:

```
info(directx11): presents: 2 in 1219ms (1.6/sec), total 26
```

**1.6 presents/sec with nothing changing**, steady across the whole run — exactly
the 600 ms cursor blink (1000/600 = 1.67). It confirms the readiness doc's
prediction: `cursorTimerCallback` notifies the general wakeup, `rebuildCells`
sets `cells_rebuilt` unconditionally, and that flag alone drives `needs_redraw`,
so every blink costs a full rebuild and a full-surface present.

Also settled in passing: **`driver=hardware feature_level=11_1`**. The earlier
worry that some benchmarks might have been measuring WARP is answered — this
machine runs the hardware rasterizer.

Next: make `cells_rebuilt` honest, which is the cheapest item on the list and the
precondition for the idle criterion under any wording.

## 8. Third sitting — the freeze had the wrong cause for three phases

The forced render, the throttle, and the 26% throughput gap all rested on one
claim: that libghostty's wakeup coalescing drops a notify arriving after the
render thread samples state. **It does not.** Reading the whole path:

- the loop does `swap(false)` before the callback (`iocp.zig:291`), but
- a notify during the callback sets the flag back *and* posts a packet, and
- `.rearm` pushes the completion back **without clearing the flag** (`:740-743`), and
- `wakeupCallback` returns `.rearm` unconditionally (`Thread.zig:588`).

So a scoping exercise that was meant to produce a fix produced a cancellation
instead, and a correction to three documents.

### What it actually was

Found by measuring instead of reading. Patch 33 adds stage counters — notify,
wakeup, update, present — **reported from the cursor blink timer**, because a
report emitted by the render path goes silent exactly when rendering stops.

```
before   notify=41 wakeup=79  update=79  present=81     <- +2/sec, the blink
after    notify=41 wakeup=404 update=404 present=406    <- +321 in one second
```

**On Windows, pty output had never woken the renderer.** `Termio`, `Options` and
`StreamHandler` held `renderer_wakeup: xev.Async` by value, and `Surface.init`
assigned a copy. libxev's async is an OS handle on Linux (eventfd) and macOS
(mach port), so copies work. The IOCP implementation keeps its state in the
struct — `wait()` sets `waiter` on the instance the loop owns — so a copy has
`waiter == null` and `notify()` sets a bool nobody reads **and returns
success**. Silent, and Windows-only. Patch 34 holds it by pointer.

It explains everything the old theory could not: why the freeze appeared in an
*unfocused* pane (the blink timer is cancelled on focus loss, so an unfocused
pane had zero wakeups and stopped dead while a focused one limped at 1.67 Hz);
why scrolling cured it and resizing did not; and why no native apprt sees it.

### The retraction

**"Forced render removed entirely = 37.4 MB/s = parity with cascadia" measured a
terminal that was not drawing.** Removing the forced render did not let the
engine run — it removed all rendering except the blink. The conclusion built on
it, that the engine was already fast enough, is dead.

| | MB/s |
|---|---|
| ghostty, wakeup fixed, forced render deleted (shipped) | 30.9, 30.9, 30.9 |
| cascadia, same session | 30.3, 37.7, 39.0, 32.3 |

ghostty's runs are identical to a tenth; cascadia's spread is nearly 30%, so the
**cascadia** figure is the shakier one and wants a quiet machine. The gap is
roughly 10–15%: not zero, and not the 25% a first reading suggested.

### Also learned

- **The engine-identity check is unreliable.** With `profiles.defaults.engine =
  ghostty`, `ghostty-internal.dll` is loaded even for a cascadia pane — it
  reported "ghostty" for three cascadia runs. The per-pane check is the search
  box's regex/case toggles, which a ghostty pane greys out.
- **The diagnostic perturbs the measurement**: 20.2 MB/s with
  `GHOSTTY_RENDER_DIAG=1` and a DBWIN listener attached, against 30.9 without.
  Never run them together.
- **The pty size bug and this one were both invisible to every existing test**,
  and both were visible on screen the whole time.

## 9. What is not done

**None of Phase 7's three exit criteria are met.** Throughput is 28.0 against cascadia's
38.1; latency has never been measured on either engine; the idle criterion cannot be
assessed until it is restated and damage gating exists.

- **The unfocused half of the repaint check** (§4) — the configuration the original freeze
  was found in.
- **The Settings UI engine dropdown has never been looked at by a human.** The evidence
  says it works — `profiles.defaults.engine` is set and nobody edited the file by hand —
  but that is inference.
- **The remaining ~26% of the throughput gap** needs the upstream wakeup re-arm fix. The
  mechanism is now pinned down exactly (a single atomic bool, swapped once per loop tick,
  with no generation counter), so it is specifiable rather than exploratory.
- **`bench-throughput.ps1` drives `hwnd-host` only.** Every pane number this phase is
  judged on — 4.2, 28.0, 37.4, 38.1 — was taken by hand, outside the script. A phase whose
  exit criterion is a throughput comparison should not have its headline numbers produced
  by a procedure that is not in the repo.
- Everything in the presentation half is untouched: damage-gated `Present1` (`Present1`
  is not even bound yet — a `Reserved` vtable slot), the waitable swap chain, occlusion,
  scroll-as-rotation.
