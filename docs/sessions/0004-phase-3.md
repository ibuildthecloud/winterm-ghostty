### Two rendering bugs found by eye, not by tests

Both were reported by the human watching a live session, and **no test covered either** —
the font tests assert ink and colour *within* a glyph's own box, and nothing checked where
that box lands. Recording them because the gap is the interesting part.

1. **Missing viewport** (`5b333f450`). `RSSetViewports` was only called from
   `Device.bindRenderTarget`, which had no callers. `ClearRenderTargetView` ignores the
   viewport while every draw is clipped entirely by it, so it presented as a correctly
   cleared, healthy surface that silently refused to draw — with no D3D error anywhere.
2. **`offset_y` measured from the wrong origin** (`896383d3b`). It was baseline-relative
   (`ascent_px - top_px + pad`) where `freetype.zig` defines the contract as
   `bitmap_top + cell_baseline`, i.e. cell-bottom-relative, which `cell_text.hlsl` depends
   on via `offset.y = cell_size.y - offset.y`. Every glyph therefore sat high by the
   descent: invisible in ordinary text, obvious against a block cursor or reverse video.

Both now have regression tests that were **mutation-verified to go red**. The `offset_y`
test needed three attempts — the first two passed with the bug present, one because its
±3.5px tolerance was wider than the 3px `cell_baseline` it was testing for.

## 6. Learnings for the plan

**Three instrumentation traps, each of which produced a false conclusion I had to retract.
These cost most of the session.**

1. **libghostty logging is off in our builds.** `global.zig` defaults stderr logging to
   `build_config.app_runtime != .none`, and we build `-Dapp-runtime=none`. Log probes are
   silent. I read that silence as "this code never runs", concluded the render pass was not
   executing, and wrongly cast doubt on Phase 1's exit criteria. Set `GHOSTTY_LOG=stderr`.
   (Session 0003 already used this; the knowledge was not carried forward.)
2. **`PrintWindow` cannot capture the D3D11 backend.** Flip-model and DirectComposition
   surfaces are composited by DWM outside the GDI paint path, so it returns the window
   brush regardless of what the GPU drew. This produced a *second* false negative on top of
   the first. `harness/wgc-shot` now exists for this and is window-scoped, which keeps the
   security property that ruled out `CopyFromScreen` after the session 0001 incident.
3. **A missing viewport is invisible.** D3D11 starts with none bound;
   `ClearRenderTargetView` ignores it while every draw is clipped entirely by it. The
   result looks like a correctly cleared, healthy surface that silently refuses to draw,
   with **no D3D error at all**. `RSSetViewports` was only called from
   `Device.bindRenderTarget`, which had no callers.

The common failure was treating absence of signal as evidence about the code instead of
first validating the instrument. Two further claims were asserted as findings when they
were guesses — that RDP explained the blank window, and that a second window was a leaked
conhost (it is the harness's own console, subsystem 3). Both were wrong.

**Other learnings:**

- `fxc /WX` caught a real defect the GLSL carries silently: `pow` on a possibly-negative
  base. HLSL's `lerp` evaluates both branches, so a NaN from the *unselected* branch
  propagates. Worth keeping `/WX`.
- The `Globals` cbuffer must be verified against the Zig `Uniforms` by *reflection*, not by
  reasoning. Two traps: `bools` is four separate bytes here but a bitmask in GLSL, and
  `Mat` stores columns (matching HLSL's default `column_major`).
- Key mapping must go scan-code → key, not VK → key: ghostty's enum is W3C
  `uievents-code`, i.e. physical positions.

## 9. Continuation: criteria 1 and 2 closed

Written after the sections above; where the two disagree, this section is later and wins.

### Criterion 1 — interactive PowerShell + TUI — MET

Full evidence in `docs/interactive-verification.md`. Summary: PowerShell reaches a prompt
with PSReadLine colouring cmdlets *as they are typed* (so per-keystroke SGR is parsed and
rendered live, not just on submit); `Get-Process` produces a correctly aligned scrolling
table; `top` renders and updates in place; JetBrains Mono ligatures shape (`->`→`→`,
`=>`→`⇒`, `!=`→`≠`, `<=>`→`⟺`) while a space-separated control line stays unligated,
which is what distinguishes real contextual shaping from naive substitution; CJK, kana and
colour emoji fall back correctly.

**Kitty keyboard protocol**, the last unverified item, read back from the byte stream:

| Sent | Received |
|---|---|
| `CSI ? u` | `ESC[?0u` — disabled |
| `CSI > 15 u` then `CSI ? u` | `ESC[?15u` — all flags set |
| press `a` | `ESC[97u` — CSI-u form |

Queryable, settable, reads back, and actually changes the encoding.

**Trap worth keeping:** the first probe used `CSI > 1 u` and saw a plain `a`, which reads
as the protocol being ignored. It is not — level 1 only *disambiguates* escape codes, so
printable keys still send their plain byte. Any level-1 test of this is uninformative.

### Criterion 2 — vttest recorded, no regressions — MET

Per-section results in `docs/vt-compliance/vttest-results.md`. Sections 2, 6, 8, 9 and 10
are assessed here for the first time (wintty's auto-feed harness could not drive them) and
all pass; section 6 now covers Secondary DA, Tertiary DA and DECREQTPARM as well. Section
11 is the only one not run. **No section regresses against wintty.**

### Section 7 (VT52) is ConPTY's behaviour, not ours

vttest section 7 does not draw its expected screen: `**Foobar` survives on two rows in
three and the bottom border is drawn twice. One cause explains both — vttest addresses
deliberately out-of-range VT52 coordinates and relies on the terminal *ignoring* the
offending axis, and the axis is clamped instead.

The cause is outside libghostty, which contains no VT52 implementation whatsoever: no
`ESC Y` or `ESC <` in `stream.zig`'s escape dispatch, no DECANM entry in `modes.zig`, and
nothing in any dependency. ConPTY parses and re-emits the child's output before libghostty
sees it. Confirmed by running the identical probe under Windows Terminal — a different
engine and renderer on the same `wsl.exe → ConPTY` path — which clamps identically, each
terminal to its own width.

This only becomes our problem if libghostty is ever fed VT52 directly, which the Phase 4/5
WT integration does not do.

### Four more instrumentation traps

This investigation took six attempts, and five of them were wrong in ways worth recording,
because every one produced a confident conclusion first:

- **`printf` inside `$( )` never reaches the terminal.** Command substitution captures the
  escape sequences along with the reply, so the probe measures nothing. Only the *reader*
  (`dd`) may live inside `$( )`.
- **VT52 state bleeds between probe arms.** An arm that enters VT52 without `ESC <` leaves
  the next arm in VT52 and poisons it — which is exactly what made an arm with no mode
  change appear to honour VT52 addressing.
- **"Out of range" is a claim about the terminal's actual size.** Column 82 is only out of
  range if the terminal is really 80 wide; a resize issued after the child started left it
  at 99 and silently voided the test.
- **Reading pixel positions off a screenshot to infer row/column is not a measurement.** It
  produced two wrong attributions here. Prefer a probe that writes bytes to a file.

The general lesson is the same one §6 records: when the renderer is the thing under test,
bypass it — `cat -v`, `stty size`, `od -c`, a file — rather than reading its output.
