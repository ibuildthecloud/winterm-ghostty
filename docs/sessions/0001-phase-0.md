# Session 0001 — Phase 0: Toolchain + baselines

Date: 2026-07-31 · Machine: SER9 (Ryzen AI 9 HX 370, **AMD Radeon 890M** integrated, 64 GB
RAM, Windows 11 Pro 26200) · Agent session, unattended after the readiness Q&A.

## 1. Outcome

The project has a git repository, a pinned toolchain, all four upstream/reference clones
with recorded pins, and an archived copy of PR #11886 that is now *more* complete than
`gh pr diff` alone (the two pre-compiled shader blobs were binary and had to be extracted
from the PR head commit separately).

Four of the five exit criteria are met. Windows Terminal builds from source on this
machine and launches as a deployed dev package running a live PowerShell session. The one
criterion that is not met produced the most valuable finding of the session:

- **Upstream ghostty does not link `libghostty.dll` on Windows/MSVC.** `zig build test`
  passes completely (3061 pass / 55 skip / 0 fail), but `zig build -Dapp-runtime=none`
  fails at the link step. Two distinct blockers, diagnosed to the line and then reverted:
  `memset` collides with `libvcruntime`, and `termio/Exec.zig` references the POSIX
  `close`/`write` symbols that the MSVC CRT does not export. wintty carries fixes for
  both, and its `src/` differs from upstream in **98 files** — the Windows gap is
  materially larger than ADR 0004's patch list assumes.
- **Windows Terminal needs no VS 2022.** WT's own `common.build.pre.props` selects the
  **v145** toolset when `VisualStudioVersion >= 18.0`, and its README ships a winget
  config for VS 2026. The whole product — native *and* WinRT/XAML — builds on the
  installed VS 2026 Community once `terminal/.vsconfig` is applied. PLAN Phase 0's
  "VS2022 + Windows SDK" is stale and should be amended.

wintty builds and runs a live `cmd.exe` session on this GPU through the
ghostty-engine/SwapChainPanel path — the behavioral reference the plan wanted, plus proof
that the composition path works on Radeon 890M.

## 5. Decisions needed

### DECISION-NEEDED 1 — Upstream ghostty needs a Windows-build patch before Phase 1's real work can start

`zig build -Dapp-runtime=none` on upstream `4d605bf` fails with two independent link errors:

```
error: lld-link: duplicate symbol: memset
    note: defined at src/quirks_memset.zig:105
    note: defined at libvcruntime.lib(memset.obj)
```
after which (with wintty's fix applied):
```
error: lld-link: undefined symbol: close    referenced by src/termio/Exec.zig:127,128,542
error: lld-link: undefined symbol: write    referenced by src/termio/Exec.zig:207
```

The first has a known one-line fix in wintty (`builtin.abi != .msvc` added to the `enabled`
condition in `quirks_memset.zig`) — small, obviously correct, and upstreamable on its own.
The second is structural: `termio/Exec.zig` calls POSIX `close`/`write` directly, and
wintty's version of that file is heavily rewritten (it also replaces `xev.Process` with a
`WaitForSingleObject` thread, because under ConPTY the child is already in ConPTY's job
object and the IOCP completion never fires).

**Why this matters beyond a build error:** ADR 0004's patch list is `init-wtf16`,
`platform-win32`, `d3d11-backend`, `dwrite-discovery`, `winkeys`, `termio-external`,
`iocp-fixes`. None of them is "make the DLL link at all on Windows". wintty's `src/`
differs from upstream in 98 files, which suggests a substantial `windows-build` patch has
to come *first* in the series, before `init-wtf16`.

**Recommendation:** add a `windows-build` patch as patch 0 of the ADR 0004 series, scoped
to exactly what the link needs (the memset guard + an `internal_os` fd shim for
`close`/`write`), harvesting from wintty (MIT). Defer the `xev.Process`/ConPTY rework — it
belongs with `iocp-fixes` and, under ADR 0006, WT owns the PTY so ghostty's `Exec` backend
is off the critical path anyway. This needs a decision because it changes an Accepted-ADR
artifact (the patch list and its order).

## 6. Learnings for the plan

1. **PLAN Phase 0 says "VS2022 + Windows SDK". That is wrong for current WT main** — it
   selects v145 under VS 2026 and its README's winget config installs VS 2026 Community.
   Amend the text to "Visual Studio 2026 (v145) with `terminal/.vsconfig` applied".
2. **Phase 3's shader-toolchain open question is answered.** PR #11886 hand-wrote HLSL and
   compiled with `fxc /T vs_5_0 | ps_5_0`, embedding the `.cso` via `@embedFile`. That is
   the SM 5.0 DXBC route, not `dxc`/DXIL, and it confirms the question's own suspicion.
   Both `fxc` and `dxc` are present in SDK 26100.8249. Recorded in
   `docs/research/pr-11886-assets/README.md`.
3. **Phase 1's readiness question "does #11886 match what the research claimed?" —
   answer: partially, and the gap matters.** The PR is explicitly *infrastructure only*.
   Its own `DirectX11.zig` header says: "Current status: infrastructure only — COM
   bindings, device lifecycle, swap chain management, and an instanced cell-grid pipeline.
   The GenericRenderer integration (Target, Frame, RenderPass, Buffer, Texture, Sampler,
   shaders) is planned for follow-up work." `DirectX11.zig` contains **no `pub fn` at
   all** — only re-exports. DESIGN.md calls #11886 the "D3D11 module base", which is fair,
   but PLAN Phase 1's "port the revived #11886 diff as the base" should not be read as
   "the GraphicsAPI contract comes for free". Phase 1 writes that contract itself.
4. **wintty is a much larger harvest source than the harvest map implies** (98 changed
   files under `src/`). Worth an explicit diff-review step at Phase 1 readiness to decide
   what is *infrastructure we must take* versus *product decisions we should not*.
5. **Attribution convention is now urgent, not Phase 9 background.** The memset fix would
   be the first harvested MIT line and it lands in Phase 1. Decide per-file header note vs
   `NOTICES` before that patch is written (PLAN Phase 9 lists this as a standing question).
6. **`gh pr diff` is not a sufficient archive** for any PR carrying binaries. If more PRs
   get archived later, fetch `refs/pull/N/head` and extract blobs.
7. **Phase 4's baseline is cheaper than expected.** WT builds and runs from source today,
   so "WT test suites pass at pre-fork levels" can have its baseline captured *now*,
   before any seam work — which is what that phase's own open question asks for.
   `bin\x64\Debug\` already contains the TAEF binaries (`TE.exe`, `Wex.Services.exe`) and
   `WindowsTerminal.UIA.Tests.dll`, so the "which suites are runnable locally" question
   can be answered by running them rather than reasoning about them.
8. **Build-machine limits belong in the scripts, not in anyone's head.** Two of the three
   WT failures this session were resource/state problems (commit charge, stale codegen)
   that looked like compiler errors. `scripts/build-terminal.ps1` now encodes all five
   gotchas in its help text so the next session does not rediscover them.
